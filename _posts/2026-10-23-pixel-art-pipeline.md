한 글자가 한 픽셀인 텍스트 격자(`.pixa`)로 스프라이트를 쓰고, Pillow로 빌드하면서 기계가 판정할 수 있는 도트 규칙은 린터로 검사하는 파이프라인을 만들었다. 이렇게 만든 에셋은 PNG로 굽지 않고 그대로 실어서 브라우저 게임에도 썼다.

| 항목 | 값 |
|---|---|
| 원본 포맷 | `.pixa` 문자 격자. `.`은 투명, `0-9a-f`는 팔레트 인덱스(최대 16색) |
| 빌드·린터 | `pix.py` 717줄, 의존성은 Pillow 하나 |
| 에셋 | `.pixa` 79개, 팔레트 44개 (전부 DawnBringer 32의 서브셋) |
| 규격 | 캐릭터 32×32 · 타일 16×16 · 소품 8×8, 화면 320×180 |
| 린트 규칙 | 포맷·gutter ERROR + 도트 품질 WARN 8종 |
| 회귀 테스트 | `test_pix.py` 전부 통과. 데모 스모크 18건, 게임 스모크 107건 × 2(연출 켬/끔), 렌더 민감도 6/6 |

## 1. 왜 텍스트 격자인가

LLM은 마우스를 쓰지 못하고 그리는 도중에 결과를 볼 수도 없어서, 그림을 그리게 하면 형태가 쉽게 무너진다. 스프라이트를 글자 격자로 두면 이 조건이 달라진다.

쓰는 동안 형태가 텍스트로 보이고, `git diff`가 그대로 픽셀 diff가 된다. 글자가 색 대신 팔레트 인덱스를 담고 있어서 팔레트 밖 색은 쓸 방법도 없다.

이 전제가 성립하는지부터 확인하려고 설계 전에 스파이크를 돌렸다. Claude가 32×32 후드 모험가를 격자에 손으로 쓰고 간이 Pillow 렌더러로 8배 PNG를 뽑아 봤는데, 빈 행 5개를 뺀 유효 행 27개 중 26행이 대칭축(x=15.5)을 정확히 지켰다. 형태는 무너지지 않았다.

![스파이크 격자와 현재 hero](/assets/img/posts/pixel-art-pipeline/spike-vs-hero.png)
_왼쪽이 스파이크에서 손으로 쓴 첫 격자(`spike/fx.hex`로 렌더), 오른쪽이 지금의 hero idle 프레임 0. 둘 다 32×32를 8배 nearest-neighbor로 키웠다_

품질은 "읽히지만 아마추어" 수준이었다. 결함을 적어 놓고 원인을 지식 부재와 실수로 나눠 보니, 사각 얼굴·줄무늬 하이라이트·평면 셰이딩 셋은 반복해서 고칠 실수라기보다 패턴을 몰라서 생긴 쪽이라고 봤다.

| 결함 | 원인 | 종류 |
|---|---|---|
| 얼굴이 모서리 없는 사각 박스 | 곡선을 어떻게 찍는지 모름 | 지식 부재 |
| 하이라이트가 세로 줄무늬라 상처처럼 보임 | 형태를 따르지 않는 배치 | 지식 부재 |
| 망토·다리가 완전 평면 | 형태 셰이딩을 모름 | 지식 부재 |
| 바닥 행이 14px 검은 막대 | 아웃라인을 밑창으로 씀 | 실수 (사용 오류) |
| 13행 오른쪽 어깨 1px 돌출 | 오타. 줄 길이 검사를 통과했다 | 실수 (오타) |

린터 설계를 바꾼 건 마지막 줄이다. 13행에 `2`를 하나 더 쓰고 뒤쪽 `.`을 하나 덜 쓴 탓에 길이는 정확히 32자였고, 줄 길이 검사는 통과했는데 그림은 1px 튀어나왔다. 자세한 얘기는 4장에서 한다.

## 2. `.pixa` 포맷

아래는 `sprites/hero.idle.pixa`의 앞부분이다. 원본이 이 파일이라 고칠 때도 여기를 고친다.

```text
@sprite  hero
@size    32x32
@palette hero
@light   upper-left-45

@frame idle/0 220
#       00000000001111111111222222222233
#       01234567890123456789012345678901
i0:00 | ................................
i0:01 | ................................
i0:02 | .............000000.............
i0:03 | ............04433220............
i0:04 | ...........0443333220...........
i0:05 | ..........044333333220..........
i0:06 | ..........041155511220..........
i0:07 | ..........041666551320..........
i0:08 | ..........0416b6b51320..........
i0:09 | ..........031155511320..........
i0:10 | ..........031111111320..........
i0:11 | .........04332222223220.........
```

설계는 세 번 평가를 받았는데(v1 위험, v2 보통, v3 통과), 포맷 결정 대부분은 v2의 구멍을 메우는 과정에서 나왔다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 글자 | `0-9a-f` 16색 | v2는 `0-9` 10색이었다. 그런데 같은 문서가 contextual outline으로 색이 11~12개가 된다고 적고 있었다. 10색 포맷에 12색은 안 들어간다 |
| gutter | `<태그 첫 글자><프레임 번호>:<행 번호> \| ` | 아래 설명 |
| 파일 단위 | 한 파일 = 한 태그 (`hero.idle.pixa`) | 태그가 섞이면 gutter 접두가 서로 다른 프레임에서 같아질 수 있다 |
| 프레임 헤더 | `@frame <tag>/<n> <ms>` 3토큰 | 스파이크 파서가 duration을 분리하지 않아 프레임 이름이 `"idle/0 200"`이 됐다 |
| 좌표 눈금 | 주석으로 권장, 강제하지 않음 | 눈금을 넣었는데도 13행 오타가 났다 |

gutter 모양은 편집 방식에서 나왔다. 격자는 Claude Code의 Edit 툴로 한 행씩 고치는데, Edit은 바꿀 문자열이 파일 안에 하나뿐이어야 한다. idle 2프레임은 두 프레임의 행이 대부분 같아서 행 번호만 붙이면 `13 | ...`가 파일에 두 번 나오고, 편집은 "유일하지 않음"으로 실패한다. 그래서 프레임 식별자를 접두로 넣어 모든 행을 유일하게 만들었다.

파서는 gutter 값도 검증한다. 행 번호가 실제 인덱스와 다르면 행이 뒤바뀐 것이고, 접두가 감싸는 `@frame`과 다르면 프레임 0 블록을 복사해 프레임 1을 만들면서 접두를 안 고친 경우다. 이 경우를 놓치면 번호 검사는 통과하는데 같은 행이 두 번 생겨서, gutter를 바꾼 의미가 아무 경고 없이 사라진다.

```python
GUTTER = re.compile(r"^([A-Za-z]\d+):(\d+)\s*\|\s?")

m = GUTTER.match(line)
if not m:
    doc.errors.append(f"{lineno}행: gutter 형식 '<접두>:<행번호> | ' 누락: {line[:20]!r}")
    continue
prefix, rownum = m.group(1), int(m.group(2))
expect = f"{frame.tag[0]}{frame.index}"
if prefix != expect:                                            # ERROR 5
    doc.errors.append(
        f"{lineno}행: gutter 프레임 접두 '{prefix}' ≠ 기대값 '{expect}' "
        f"(@frame {frame.tag}/{frame.index}). 프레임 복사 후 접두 미갱신 의심"
    )
if rownum != len(frame.rows):                                   # ERROR 4
    doc.errors.append(
        f"{lineno}행: gutter 행번호 {rownum} ≠ 실제 인덱스 {len(frame.rows)}"
    )
frame.rows.append(line[m.end():])
frame.linenos.append(lineno)
```

`(tag, index)`가 중복된 프레임도 같은 이유로 ERROR다. 같은 PNG 경로를 덮어쓰고 gutter 행도 비유일해진다. 줄 수·줄 길이·팔레트 밖 글자는 기본이 ERROR이고, ERROR가 하나라도 있으면 렌더하지 않는다.

팔레트는 스프라이트마다 `.hex` 파일 하나를 둔다. 한 줄에 6자리 hex를 하나씩 쓰고 주석은 `#`으로 단다. 아웃라인 색 집합도 팔레트 안에서 `# @outline 0 1 7` 한 줄로 선언한다(4.3절).

## 3. 렌더러와 리포트

{% include embed/video.html src='/assets/img/posts/pixel-art-pipeline/explainer.mp4' poster='/assets/img/posts/pixel-art-pipeline/explainer-poster.jpg' title='.pixa 스프라이트 하나가 파서와 린터를 통과하고 빌드 리포트를 거쳐 PNG로 굽지 않은 채 게임 캔버스에 실리는 과정' loop=true %}

렌더러는 짧다. 인덱스를 팔레트 색으로 바꿔 찍고 확대는 nearest-neighbor 정수배로만 한다.

```python
def render(rows: list[str], pal, w: int, h: int, scale: int = 1) -> Image.Image:
    img = Image.new("RGBA", (w, h), (0, 0, 0, 0))
    px = img.load()
    for y, row in enumerate(rows):
        for x, ch in enumerate(row):
            if ch != TRANSPARENT:
                px[x, y] = (*pal[DIGITS.index(ch)], 255)
    return img if scale == 1 else img.resize((w * scale, h * scale), Image.NEAREST)
```

GIF는 P 모드로 만든다. GIF 팔레트의 인덱스 0을 투명으로 예약해 두고 `.pixa` 인덱스를 1씩 밀어서 싣고, 프레임별 duration에는 `@frame`의 ms를 그대로 넘긴다.

`python pix.py build`가 내는 산출물마다 맡은 역할이 있다.

| 산출물 | 역할 |
|---|---|
| 8x PNG | 품질 결함 발견. 사각 얼굴·평면 셰이딩·하이라이트 오배치를 전부 이걸로 찾았다 |
| 실루엣 격자 (`#`/`.`, 행 번호 포함) | 기하 오류를 처음 발견하는 곳 |
| 엣지표 (행별 L, R, 폭, 중심) | 기하 오류의 위치 확정 |
| 팔레트 사용표 + 휘도 열 | 실제로 쓰인 명도 단계 수. ΔL<5인 색은 한 밴드로 묶어 센다 |
| 프레임별 bottom-y 한 줄 | 발 드리프트를 숫자로 비교 |
| 프레임 delta 격자 | 전신 수직 오프셋을 뺀 뒤 무엇이 움직였는지 |
| 1x PNG, GIF, 타일 시트 | 실제 에셋과 루프 확인 |

스파이크의 13행 오류는 엣지 계산으로 찾은 게 아니다. 스파이크 렌더러에는 엣지 계산이 아예 없었고, 출력된 실루엣 격자를 보다가 13행만 넓은 게 눈에 들어왔다. L/R/center는 그다음에 임시 스크립트로 계산해서 위치를 확정했다. 그래서 실루엣 격자는 "발견자", 엣지표는 "확정자"로 나눠 둘 다 남겼다.

종료 코드는 `0` 깨끗, `1` ERROR, `3` WARN만 남음, `2` usage error다. 처음엔 WARN에 2를 줬는데 그러면 오타 난 명령이 CI에서 "경고는 있지만 성공"으로 읽힌다. 여러 파일을 빌드할 때는 `max(codes)`도 못 쓴다. 심각도는 ERROR > WARN > 깨끗 순인데 코드 값은 1 < 3이라서 ERROR가 WARN에 묻힌다.

```python
codes = [build(p, verbose) for p in targets]
if not codes:
    return 2                      # usage error
# 심각도 순서는 ERROR > WARN > 깨끗. 코드값(1,3,0)의 대소와 다르므로 max 를 쓰면 안 된다.
return 1 if 1 in codes else (3 if 3 in codes else 0)
```

여기는 실제로 한 번 깨졌다. `build()`의 반환형을 bool에서 int로 바꾸면서 조기 반환 두 곳이 `return False`로 남았고, `False == 0`이니 팔레트 오류가 "깨끗"으로 보고됐다. 지금은 종료 코드 7가지 경우를 테스트로 고정해 뒀다.

## 4. 린터가 잡는 규칙과 그 이유

| 레벨 | 규칙 | 잡는 것 |
|---|---|---|
| WARN 1 | 엣지 국소 극값 | 길이가 상쇄된 격자 오타 |
| WARN 2 | 프레임 간 색 집합 변화 (타일셋 제외) | 애니메이션 깜빡임 |
| WARN 3 | 휘도 인접 (ΔL<5 쌍이 8-이웃으로 맞닿음) | 흑백에서 형태 소실 |
| WARN 4 | 타일 경계 상태 | blob47 타일 생성기 버그 |
| WARN 5 | 아웃라인 무결성 | 밝은 색이 배경에 노출 |
| WARN 6·7 | 실루엣 경계 1px · 내부 디테일이 경계에 붙음 | 눈이 아웃라인에 흡수되어 몸통이 뚫림 |
| WARN 8 | 잡음 (고립 픽셀 8개 초과 그리고 칠한 칸의 10% 초과) | 흩어진 점, 끊긴 줄무늬 |

### 4.1 엣지 국소 극값: 정당한 전이는 단조롭고, 오타는 튄다

스파이크 13행 주변의 엣지는 이랬다.

| row | 길이 | L | R | center |
|---|---|---|---|---|
| 12 | 32 | 8 | 23 | 15.5 |
| 13 | 32 | 7 | 25 | 16.0 |
| 14 | 32 | 7 | 24 | 15.5 |

R이 23 → 25 → 24로 올라갔다가 내려온다. 처음 떠올린 규칙 후보는 이 신호와는 다른 것들이었다. 세 후보를 정상본, 오류본, 그리고 한쪽 팔을 4행 내밀고 하체를 2px 치우친 합성 비대칭본에 돌려 비교했다.

| 규칙 | 정상본 오발화 | 13행 오류 | 비대칭본 경고 |
|---|---|---|---|
| 전역 대칭: `(L+R)/2 ≠ 중앙값` | 0 | 검출 | 9건 |
| 이웃 행 엣지 불연속 ≥2 | 2건 | 검출 | 7건 |
| 국소 극값: 엣지가 양쪽 이웃 행보다 바깥 또는 안쪽 | 0 | 검출 | 3건 |

전역 대칭은 스타일 원칙과 부딪힌다. 도트 캐릭터는 완전 좌우 대칭을 피하는 게 정석인데 이 규칙은 거기에 벌점을 주고, walk 사이클에서는 아예 쓸 수가 없다. 이웃 행 불연속은 정상본에서 벌써 2건 오발화했다. 오발화한 곳은 23·24행에서 허리가 좁아지는 구간(L 8→10, R 23→21)으로, 정당한 단조 전이다. 오타 쪽은 극값 모양으로 나타났다.

```python
def lint_extrema(doc: Doc, fr: Frame, w: int) -> None:
    es = edges(fr.rows, w)
    for y in range(1, len(es) - 1):
        prev, cur, nxt = es[y - 1], es[y], es[y + 1]
        if not (prev and cur and nxt):
            continue
        (_, pl, pr), (_, cl, cr), (_, nl, nr) = prev, cur, nxt
        if (cl < pl and cl < nl) or (cl > pl and cl > nl):
            doc.warns.append(f"[{fr.name}] {y}행 좌엣지 국소 극값: {pl} → {cl} → {nl}")
        if (cr > pr and cr > nr) or (cr < pr and cr < nr):
            doc.warns.append(f"[{fr.name}] {y}행 우엣지 국소 극값: {pr} → {cr} → {nr}")
```

빈 행을 건너뛰어 이어 붙이지 않고 실제로 인접한 세 행만 비교한다. 이어 붙이면 몸통과 떨어진 덩어리가 몸통의 이웃 행처럼 취급돼서 오발화한다. 첫 행과 마지막 유효 행은 이웃이 하나뿐이니 검사에서 뺀다.

다만 이 순위는 오류 표본 한 종류(한 행, 1px, 고립)에서만 성립하고, 표본을 넓히면 국소 극값에도 구멍이 보인다.

| 오류 유형 | 전역 대칭 | 이웃 불연속 | 국소 극값 |
|---|---|---|---|
| 1행 고립 오타 | 검출 | 검출 (+오탐 4) | 검출 |
| 2행 연속 오타 | 검출 | 검출 | 무검출 |
| 3행 연속 오타 | 검출 | 검출 | 무검출 |
| 내부 오류 (실루엣 불변, 벨트 1px) | 무검출 | 무검출 | 무검출 |

극값은 엄격 부등호를 쓰니 평탄 구간에서는 사라진다. 앞 행을 베껴 쓰다가 오타가 따라 번지는 건 충분히 일어날 만한 일인데도 규칙은 고치지 않았다. 평탄 구간을 처리하려면 정상본의 어깨 평탄부(R=24가 연속되는 14~16행)와 구분해야 하고, 그러다 보면 "평탄 길이 ≤2" 같은 임계값 튜닝이 시작된다. 그 대신 연속 오타본 `fx-plateau.pixa`를 커밋하고 "현재 무검출"을 테스트로 고정했다. 나중에 규칙이 바뀌면 이 테스트가 먼저 알려 준다.

내부 1px 오류는 어떤 규칙으로도 못 잡는다. 8x PNG를 눈으로 보는 것 말고는 확인할 방법이 없어서 작업 루프에서 VIEW 단계를 뺄 수 없다.

### 4.2 휘도 인접은 문서로 관리하면 팔레트를 못 따라간다

흑백으로 바꿨을 때 구분되지 않는 두 색을 맞붙이면 형태가 사라진다. 처음엔 스타일 가이드에 "인접 금지 쌍" 표를 적어 두고 서술 규칙으로 관리했는데, 팔레트를 고칠 때마다 쌍이 바뀌는 바람에 두 번 회귀해서 규칙으로 올렸다. 빌드할 때마다 팔레트의 휘도를 새로 계산하니 문서가 낡을 일이 없다.

```python
def lint_value_adjacency(doc: Doc, fr: Frame, pal) -> None:
    lum = {DIGITS[i]: luma(c) for i, c in enumerate(pal)}
    hits = []
    for y, row in enumerate(fr.rows):
        for x, ch in enumerate(row):
            if ch == TRANSPARENT:
                continue
            for dy, dx in ((1, 0), (0, 1), (1, 1), (1, -1)):   # 8-이웃 (중복 없이 절반만)
                if not (0 <= y + dy < len(fr.rows) and 0 <= x + dx < len(row)):
                    continue
                other = fr.rows[y + dy][x + dx]
                if other in (TRANSPARENT, ch):
                    continue
                if abs(lum[ch] - lum[other]) < VALUE_BAND:
                    hits.append((x, y, ch, other))
    # ... 생략 (경고 메시지 구성)


def luma(rgb) -> float:
    r, g, b = rgb
    return 0.2126 * r + 0.7152 * g + 0.0722 * b
```

휘도는 Rec.709 가중치로 계산하고 임계 `VALUE_BAND`는 5다. 처음엔 4-이웃만 봤는데, 이 규칙을 만든 계기였던 벨트 모서리 충돌이 대각으로 한 칸 밀린 채 남아 있어서 8-이웃으로 넓혔다. 오른쪽, 아래, 아래쪽 두 대각선까지 네 방향만 보면 8-이웃 쌍을 한 번씩만 세게 된다.

그런데 이 규칙이 실제로 살아 있는 건 hero뿐이다. 지금 팔레트에서 색 쌍의 최소 휘도차를 재면 hero 12색이 1.24, slime 7색이 21.42, terrain 6색이 18.15로, slime과 terrain은 간격이 임계 5보다 넓어서 이 규칙이 구조상 발화할 수 없다. 실산출물의 WARN 0을 "검증됐다"로 읽으면 안 되는 경우라서, 어느 팔레트에서 규칙이 발화할 수 있는지를 테스트가 출력하고 고정한다. 규칙 자체가 모르는 새 망가지는 것도 막아야 하니, 전용 팔레트로 충돌이 정확히 1건 나는 양성 픽스처와 ΔL 42 쌍이 발화하면 안 되는 음성 대조군도 함께 둔다.

### 4.3 아웃라인과 실루엣 규칙의 0건은 깨끗하다는 뜻이 아니었다

WARN 5는 투명과 맞닿은 픽셀은 아웃라인 색이어야 한다는 규칙이다. 타일 바깥 코너를 1px 깎았더니 팔레트에서 가장 밝은 색이 아웃라인 없이 배경에 드러난 적이 있다. 테두리를 한 변씩 (아웃라인 + 전이)로 칠하다 보니 나중 변의 전이가 먼저 칠한 변의 아웃라인을 덮어 버린 탓이었다.

이 규칙에서 "0건인데 깨끗하지 않은" 경우가 세 번 나왔다.

1. 처음엔 이 규칙이 `blob47` 선언 뒤에 있어서 스프라이트에서는 한 번도 돈 적이 없었다. 게이트를 떼자마자 hero에서 실제 위반 29px이 나왔다.
2. 캔버스 밖을 투명으로 세지 않아 heart의 (0,2)에 있는 팔레트 최고 휘도 색이 왼쪽 끝에 아웃라인 없이 노출된 걸 놓쳤다. 실루엣 규칙은 캔버스 밖을 투명으로 세고 있었으니 두 규칙이 서로 다른 캔버스를 본 셈이다.
3. 격자를 무작위로 25px씩 망가뜨린 20개에 규칙을 돌리면 20/20이 잡히는데, 저작 스크립트의 `outline_close`를 거치면 11/20만 남는다. 생성기와 검사기가 같은 술어를 쓰기 때문이고, 남은 11개는 전부 캔버스 가장자리다. 저작을 거친 스프라이트라면 캔버스 안쪽에서 이 규칙이 발화할 일이 없으니, 규칙을 지우지 않고 이 성질을 테스트가 출력하게 했다.

hero는 망토·피부·가죽이 각자 램프를 쓰고 아웃라인도 `0`·`1`·`7` 셋이다. 규칙을 인덱스 0에 고정하면 hero에서 프레임당 26~40건이 오발화하므로 아웃라인 집합은 팔레트가 선언하게 했다. 다만 선언에 상한이 없으면 선언만으로 규칙을 꺼 버릴 수 있다. hero.attack에 12색을 전부 선언하면 위반이 26·28·36·29건에서 0·0·0·0건으로 떨어진다. 그래서 선언 개수를 팔레트 색 수의 3분의 1로 묶었다.

```python
cap = max(1, ncolors // 3)
if len(declared) > cap:
    raise ValueError(
        f"{path}: @outline {len(declared)}개는 {ncolors}색 팔레트의 상한 {cap}개를 넘는다. "
        "선언으로 규칙을 침묵시키지 못하게 하는 하한이다")
```

hero 12색이면 상한이 4개라 3개 선언은 통과한다.

WARN 6·7(실루엣)은 슬라임을 16×16으로 줄였을 때 생겼다. `draw_slime.body()`를 16으로 돌리자 2×2 눈이 실루엣 가장자리에 걸려 오른쪽 눈동자가 아웃라인에 흡수되고 몸통이 뚫렸는데, 그 격자가 ERROR 0 / WARN 0으로 통과했다. 지금은 인덱스 0의 아웃라인을 경계 성분과 내부 성분으로 나눠, 경계 성분이 1px보다 두꺼운 곳과 내부 성분이 경계에 붙은 곳을 경고한다. 이 규칙도 범위가 좁아서, 실루엣 안쪽에 인덱스 0 픽셀이 있어야 하니 79종 중 8종에서만 발화할 수 있다. 그 목록은 테스트가 출력한다.

### 4.4 한 번 버린 고립 픽셀 규칙이 잡음 규칙으로 돌아왔다

설계 v2에는 "4-이웃이 전부 다른 색인 픽셀" 규칙이 있었다. 스파이크 hero에 돌리니 11건이 나왔는데, 그중 10건은 눈 2개(32×32에서 1px 눈은 표준)와 후드·망토 아웃라인 곡선의 모서리 8개로 전부 의도한 픽셀이었다. 하나 남은 진짜 결함 (25,13)은 국소 극값이 이미 잡는 13행 오타였으니 이 규칙만의 검출력은 0이었고, 그래서 지웠다.

나중에 다시 필요해진 건 밀도를 보는 규칙이었다. 점 한두 개는 디테일이지만 칠한 칸의 10%가 흩어진 점이면 모래알처럼 보인다. 그래서 고립의 정의를 8방향으로 넓히고 두 조건을 모두 넘을 때만 경고하게 했다.

```python

# 많은 작은 스프라이트는 화살(깃털 두 색 + 촉, 프레임당 6)이라 그 위 +2 여유로 8. 비율: 캐릭터는
```

규칙을 켜자마자 모래 회오리가 걸렸다.

_위가 수정 전, 아래가 수정 후. 16×16 3프레임을 8배로 키웠다_

줄무늬 기울기가 2라서 한 줄씩 건너뛰다 보니 선이 끊긴 점이 됐다. 수정 전 격자를 지금 린터로 다시 재면 프레임별 고립 픽셀이 28·27·29개(칠한 122칸의 22~24%)이고, 기울기를 1로 바꾸고 나서는 0·2·1개다.

캔버스 가장자리를 보는 방식은 에셋 종류마다 다르다. 스프라이트는 밖을 투명으로 보고, 꽉 찬 채움 타일은 같은 타일이 이어 붙으니 반대쪽 가장자리를 이웃으로 본다(wrap). blob47 타일은 옆에 어떤 타일이 올지 모르니 가장자리 칸은 아예 세지 않는다. 처음엔 전부 투명으로 봤는데, 그 탓에 바위 채움 타일에서 나온 고립 4개가 모두 가장자리의 거짓 고립이었다.

의도한 한 점(눈, 버클, 2px 손)은 경고하지 않고, 그 대신 테스트가 파일별 고립 픽셀 수를 고정한다. 지금은 55개 파일에서 색 고립이 1,193개, 몸 안에 떨어진 아웃라인 외톨이가 64개이고, 이 수가 늘어나면 테스트가 실패한다.

### 4.5 타일 경계에서는 틀린 불변식이 완화를 낳았다

blob(Wang) 타일셋의 이음새 검사는 처음에 "인접한 타일의 경계는 같아야 한다"로 잡았는데, 불변식부터 틀렸다. A 아래가 비어 있고 B 아래가 잔디면 지형이 실제로 다르니 두 경계도 달라야 한다. 안 맞는 부분은 "코너 구역 제외"로 덮었다. 그런데 그 제외 구간 `slice(border, size-border)`에 하한이 없어서, `@blob47 8`이면 빈 문자열끼리 비교되고 린트 전체가 아무 말도 하지 않게 됐다.

지금 쓰는 불변식은 한 변의 픽셀이 (그 변이 열려 있는가, 수직인 두 변이 열려 있는가, 그 변 양 끝에 안쪽 모서리가 있는가)로 완전히 결정된다는 것이다. 상태가 같은데 경계가 다르면 생성기 버그다. 경계 16px 전체를 보니 덮을 구간도 우회할 파라미터도 없다.

### 4.6 완화에는 상한을 둔다

망치·번개·별 같은 아이콘은 불규칙한 실루엣이 곧 정체성이라 국소 극값에 계속 걸린다. `@silhouette irregular`를 선언하면 극값 규칙 하나만 꺼지고 아웃라인·휘도·실루엣 규칙은 그대로 돈다. 어느 파일이 이 선언을 했는지는 테스트가 목록으로 고정하는데, 지금 28개이고 아이콘·든 무기·로비 소품·전갈·화살·스미어뿐이다. 바위 채움 타일처럼 캔버스 밖을 투명으로 세지 않는 `@edge closed` 선언도 같은 방식으로 목록을 고정한다. 앞에서 `@outline`에 상한을 둔 것과 같은 이유로, 완화에 상한이 없으면 `@blob47 8` 때 같은 일이 또 생긴다.

## 5. 팔레트와 해상도 제약

| 항목 | 값 | 근거 |
|---|---|---|
| 캐릭터 캔버스 | 32×32 | 눈·표정을 표현할 수 있는 하한 |
| 타일 | 16×16 | 32px 캐릭터가 타일 2칸 |
| 목표 화면 | 320×180 | 16:9 정수배. 1080p에서 6배, 4K에서 12배 |
| 확대 | 정수배 nearest-neighbor만 | 1.5배·회전 금지 |
| 색 수 | 캐릭터 7~12색, 타일·소품 4~6색 | hero 12 · slime 7 · terrain 6 · bat 6 · heart 4 · coin 4 |
| 팔레트 출처 | DawnBringer 32 서브셋 | 새 색을 만들지 않는다 |

"DB32에서 발췌했다"는 말은 처음엔 아무도 확인하지 않았는데, 대조할 `palettes/db32.hex`가 없었기 때문이다. 지금은 테스트가 `palettes/*.hex`를 전부 훑어서 44개 팔레트가 DB32 32색의 서브셋인지 확인한다. 이 검사도 처음엔 팔레트 이름을 손으로 나열한 목록을 썼던 터라, 그 뒤로 팔레트가 13개 늘어나는 동안 절반만 보면서 "전 팔레트 서브셋"이라고 출력하고 있었다.

hero 팔레트는 램프 셋으로 짰고, 화면에서 면적이 가장 넓은 망토에 단을 가장 많이 줬다.

| 램프 | 인덱스 | luma 진행 | hue 진행 (HSV, hex에서 직접 계산) |
|---|---|---|---|
| 망토 (5단) | `0` `1` `2` `3` `4` | 34 → 48 → 76 → 116 → 131 | 246 → 319 → 0 → 354 → 24 |
| 피부 (3단, 아웃라인 `1` 공유) | `1` `5` `6` | 48 → 96 → 168 | 319 → 19 → 30 |
| 가죽 (4단) | `7` `8` `9` `a` | 58 → 74 → 112 → 144 | 162 → 51 → 42 → 66 |

hue는 어두운 쪽을 차갑게, 밝은 쪽을 따뜻하게 돌린다. 망토는 남보라에서 시작해 주황으로 끝난다. 가죽 아웃라인 `7`(162°, 청록)은 나머지 가죽색(42~66°)과 120° 떨어진 별개 계열이라 매끄럽게 이어지는 램프는 아니다. 채도가 16.7%로 낮아서 "차가운 저채도 최암부"로 쓰고, 스타일 가이드에도 명시적 예외로 적어 뒀다.

아웃라인은 contextual outline이라 검정 단색 대신 맞닿은 재질 램프의 최암부를 쓴다. 망토는 `0`, 피부는 `1`, 가죽은 `7`이다. "아웃라인이 맞닿은 재질과 같은 램프인가"는 팔레트에 램프 메타데이터가 있어야 검사할 수 있어서 자동화하지 않고 눈으로 지킨다.

팔레트를 크게 바꾼 적도 한 번 있다. 초기 hero는 픽셀의 64%가 L47~76 구간에 몰려 있어서 흑백으로 보면 형태가 읽히지 않았다. 망토 램프를 4단에서 5단으로 늘리고 몸통 주색을 L76에서 L116으로 올려 한 밴드에 몰린 걸 풀었고, 색 수는 12색 그대로 뒀다.

스프라이트에 그리지 않기로 한 것도 있다. 지면 그림자를 스프라이트 안에 그리면 발밑에 검은 막대가 붙었고, 이 문제가 스파이크와 첫 산출물에서 두 번 재현됐다. 단일 스프라이트로는 '캐릭터 뒤'라는 순서를 표현할 수 없으니 그림자는 엔진 몫이다. 지금은 엔진이 16×5 타원 그림자를 캐릭터보다 먼저 그린다.

## 6. 반복으로 안 고쳐지는 건 계산으로

설계 단계에서 "반복 루프를 돌리면 품질이 오른다"를 가설로 세우고, 루프 상한 5회를 돈 뒤에도 얼굴이 사각 박스이거나 망토에 형태 셰이딩이 없으면 기각한다는 반증 조건을 미리 적어 뒀다. 결과는 부분 기각이었다.

| 항목 | 결과 |
|---|---|
| 셰이딩·구조 | 반복으로 고쳐졌다. "망토가 완전 평면"이 3회 만에 5단 램프 + 림라이트 + AO가 됐다 |
| 기하 곡선 | 반복으로 못 고쳤다. "얼굴이 사각 박스"를 4회 도는 동안 모서리를 1/4개밖에 못 깎았다 |

곡선은 추측을 그만두고 계산으로 구했다. `refs/shapes.py`는 픽셀 중심을 반칸 격자로 옮긴 뒤 타원 부등식을 정수만으로 평가한다.

$$
(2x - w + 1)^2 h^2 + (2y - h + 1)^2 w^2 \le w^2 h^2
$$

```python
def ellipse(w: int, h: int) -> list[str]:
    """w×h 채워진 타원. 정수 부등식만 쓴다."""
    rows = []
    for y in range(h):
        dy = 2 * y - h + 1
        row = "".join(
            "#" if (2 * x - w + 1) ** 2 * h * h + dy * dy * w * w <= w * w * h * h else "."
            for x in range(w)
        )
        rows.append(row)
    return rows
```

6×6에서 y=0이면 dy=−5이고, 조건은 $(2x-5)^2 \cdot 36 + 25 \cdot 36 \le 1296$, 즉 $(2x-5)^2 \le 11$이다. $|2x-5| \le 3$이니 x는 1~4이고 폭은 4다. 이렇게 행별 폭을 구하면 `(4,6,6,6,6,4)`가 나오는데, 손그림을 이 값과 대조하자 위 모서리만 깎고 아래는 직각으로 둔 게 바로 드러났다. 지금 얼굴 개구부는 5×4 타원의 계산값 `3-5-5-3`을 그대로 쓴다.

이 파일의 docstring이 거짓말을 한 적도 있다. "정수 연산만 쓰므로 검증된다"고 적어 놓고 실제로는 부동소수 샘플링으로 구현돼 있었다. 지금 코드는 위의 정수 부등식을 쓴다.

타일셋에도 같은 판단을 적용했다. 47장을 손으로 그리면 752행이 되고, 그렇게 그린 이음새가 맞으리란 보장이 없다. 그래서 손으로는 브러시(베이스, 네 방향 테두리, 안쪽 모서리)만 그리고 47장은 마스크에 따라 조합한다. 47이라는 숫자도 문서에서 베끼지 않고, `refs/blob47.py`가 8방향 비트를 정규화해 256가지에서 47가지를 직접 센다. 계산 결과가 47이어야 비트 규약을 제대로 옮겼다고 볼 수 있어서다.

![타일셋으로 깐 씬](/assets/img/posts/pixel-art-pipeline/scene.png)
_blob 47타일 + 변형 타일로 깐 맵에 hero를 얹은 화면_

이 씬 맵은 47종 중 16종만 밟아서 나머지가 옳은지는 확인할 수 없었고, 그래서 47종을 전부 밟는 카탈로그 맵을 따로 만들었다. 변형 타일 배치에도 버그가 있었다. `(x*7+y*13)%4`는 7≡3, 13≡1 (mod 4)이라 `(3x+y)%4`와 같아서, 16px 타일 4칸, 즉 64×64px마다 완전히 반복됐다. 지금은 공간 해시로 고른다.

두 번째 캐릭터를 slime으로 고른 것도 이 경로를 시험해 보기 위해서였다. slime은 사지가 없는 둥근 덩어리이고, 형태는 코드가 `ellipse()`를 직접 호출해 받아 온다. 16×16 미니 슬라임도 같은 `body()` 호출로 만들었으니 손으로 찍은 픽셀이 0이다. 다만 "기하를 계산이 조달하면 크기 변경이 공짜"라는 주장은 부분적으로만 맞았다. `body()`가 `GROUND=29` 같은 32px 전용 상수를 쥐고 있어서 파라미터로 빼야 했고, 눈도 2×2에서 1px로 줄여야 했다.

## 7. 브라우저 게임에 연결하기

![게임 화면](/assets/img/posts/pixel-art-pipeline/game.png)
_게임 초기 빌드의 화면. 320×180 캔버스를 3배 nearest-neighbor로 키웠다_

게임은 에셋을 반복해서 보려고 만들었다. 데모는 30초면 끝나서 hop 사이클이 어색해도 눈에 안 띄지만, 웨이브를 오래 버티다 보면 같은 프레임을 수백 번 보게 된다.

### PNG로 굽지 않는다

`tools/make_demo.py`의 `load()`가 `.pixa`를 `pix.parse`로 읽어 격자 문자열과 팔레트를 JSON으로 싣고, `make_game.py`도 이 함수를 그대로 가져다 쓴다. 원본이 그대로 런타임 데이터가 되니 중간 산출물이 원본과 어긋날 일이 없다.

```python
def load(rel: str) -> dict:
    doc = pix.parse(ROOT / rel)
    pal = pix.load_palette(ROOT / "palettes" / f"{doc.meta['palette']}.hex")
    w, h = (int(v) for v in doc.meta["size"].lower().split("x"))
    pal_path = ROOT / "palettes" / f"{doc.meta['palette']}.hex"
    # 아웃라인 색 집합(`@outline 0 1 7`)도 싣는다. 흰 플래시판이 테두리를 남기려면 필요하다.
    # 0 만 남겼더니 미라·파라오의 다리 테두리(7번)가 흰색이 되어 모래에 번졌다.
    return {"w": w, "h": h, "pal": ["#%02x%02x%02x" % c for c in pal],
            "outline": sorted(pix.load_outline(pal_path, len(pal))),
            "frames": [{"ms": fr.ms, "rows": fr.rows} for fr in doc.frames]}
```

브라우저에서는 `bake()`가 프레임마다 격자를 오프스크린 캔버스에 한 번 굽는다. 흰 플래시판(맞은 순간 70ms)은 선언된 아웃라인만 남기고 나머지를 흰색으로 칠한 판인데, 처음 쓸 때만 굽는다. 아이콘이나 타일처럼 한 번도 번쩍이지 않는 에셋도 있어서다.

```js
function bake(sprite, pal) {
  const keep = new Set(sprite.outline || ['0']);          // 흰판에서도 남기는 아웃라인 색
  const paint = (fr, white) => {
    const cv = new OffscreenCanvas(sprite.w, sprite.h);
    const ctx = cv.getContext('2d');
    const img = ctx.createImageData(sprite.w, sprite.h);
    for (let y = 0; y < sprite.h; y++) {
      for (let x = 0; x < sprite.w; x++) {
        const ch = fr.rows[y][x];
        if (ch === '.') continue;
        const hex = white && !keep.has(ch) ? '#ffffff' : pal[parseInt(ch, 16)];
        // ... 생략 (hex를 RGBA로 풀어 img.data에 기록)
      }
    }
    ctx.putImageData(img, 0, 0);
    return cv;
  };
  return sprite.frames.map(fr => {
    let wcv = null;
    // 흰판은 **처음 쓸 때** 굽는다. 아이콘·타일은 한 번도 번쩍이지 않는다
    return { cv: paint(fr, false), ms: fr.ms, get white() { return wcv || (wcv = paint(fr, true)); } };
  });
}
```

`bake(sprite, pal)`에 다른 팔레트를 넘기면 같은 격자에서 변종이 나온다. 격자에 색 대신 인덱스가 들어 있어서 가능한 일인데, 이 포맷을 쓰면서 실제로 가장 덕을 본 부분이다.

![같은 격자, 다른 팔레트](/assets/img/posts/pixel-art-pipeline/palette-swap.png)
_slime idle 프레임 0을 `slime.hex`와 `slime-red.hex`로 렌더했다. 격자는 한 글자도 다르지 않다_

에셋 검증 데모의 붉은 슬라임, 진화 무기의 금빛 아이콘, 금빛 성검 궤적, 사막 맵의 모래 바닥과 사암 기둥이 전부 이렇게 만들었다. 다만 사막 바닥과 기둥은 런타임에 색만 바꾸는 데서 그치지 않고, `tools/make_biome.py`가 `@palette` 줄만 바꾼 `.pixa` 복사본을 따로 남긴다. 색이 바뀌면 휘도·아웃라인 규칙 결과가 달라질 수 있으니 새 팔레트로도 린터를 다시 돌리려는 것이다.

### 정수 배율은 디바이스 픽셀 기준으로

내부 해상도는 항상 320×180이다. 정수배를 CSS px 기준으로 맞추면 Windows 125%/150% 표시 배율에서 소스 1px이 디바이스 3.75px이 되고 픽셀 폭이 들쭉날쭉해진다. 그래서 배율은 디바이스 픽셀 기준으로 잡고 CSS 크기를 거꾸로 계산한다.

```js
const dpr = devicePixelRatio || 1;
const maxW = innerWidth * dpr, maxH = innerHeight * dpr;
const s = Math.max(1, Math.min(Math.floor(maxW / VW), Math.floor(maxH / VH)));
cv.width = VW; cv.height = VH;                  // 내부 해상도는 항상 320x180
cv.style.width = (VW * s / dpr) + 'px';         // 디바이스에서 정확히 s 배
cv.style.height = (VH * s / dpr) + 'px';
// ... 생략
st.style.left = Math.floor((maxW - VW * s) / 2) / dpr + 'px';
st.style.top = Math.floor((maxH - VH * s) / 2) / dpr + 'px';
```

가운데 정렬도 직접 계산한다. flex 가운데 정렬에 맡겼더니 남는 폭이 홀수일 때 캔버스가 반 픽셀(예: y=58.5)에 놓여서 도트 전체가 번졌다. 스프라이트를 찍을 때도 `Math.round`로 좌표를 정수에 맞추고 매 프레임 `imageSmoothingEnabled = false`를 건다. 캔버스 위에 겹치는 DOM 글자는 캔버스 1픽셀의 CSS 크기(`--u`)의 배수로만 크기를 잡았기 때문에 배율이 3배든 6배든 그림과 함께 커진다. 한글에는 픽셀 폰트 갈무리 7·9·11을 쓰고, 글자 1픽셀이 캔버스 반 픽셀이 되도록 디바이스 정수 픽셀로 내린다.

### 격자에서 읽는 것들

캐릭터가 든 무기는 몸에 굽지 않고 따로 그린 뒤, 빌드가 캐릭터 격자에서 읽은 손 위치에 맞춰 얹는다. 손은 팔 행(14~21)의 피부색(`5`·`6`) 픽셀 중 가장 왼쪽이나 오른쪽에 있는 것으로 본다. 위치 표를 손으로 관리하면 팔 동작을 고쳤을 때 표가 낡아서 무기가 허공에 뜬다.

로비 배경은 로컬 확산 모델(`sd-turbo`, CPU, 4스텝)로 한 장 굽고 320×180·24색으로 양자화해서 인덱스 격자로 넣었는데, 렌더 경로를 하나로 유지하고 싶어서였다. 57,600칸을 문자로 넣어도 크기는 PNG base64(39KB)와 비슷하다.

### 헤드리스 검사

`tools/demo_smoke.js`와 `game_smoke.js`는 node `vm`으로 브라우저 없이 실제 게임 루프를 돌린다. `raster.js`가 픽셀을 실제로 쌓는 2D 컨텍스트라서 420프레임을 래스터라이즈한 누적 해시를 비교할 수 있다. 해시가 무엇을 잡는지도 따로 증명해야 하니, 렌더를 6가지로 망가뜨려 전부 잡히는지 매번 확인한다. JS 255줄을 `engine.js`와 `demo.js`로 나눌 때는 옮기기 전에 기준 해시를 찍어 뒀고, 분리한 뒤에도 해시가 같았다.

## 8. 실패 사례

틀린 건 지우지 않고 표로 남겨 왔다. 그중 파이프라인 쪽에서 특히 쓸모 있었던 것만 골랐다.

### 파이썬 테스트 30건 통과, 데모는 SyntaxError

슬라임 커밋에서 중괄호 없는 `if` 본문에 `const`를 넣어 데모 전체가 SyntaxError로 죽은 채 나갔다. 파이썬 테스트 30건은 전부 통과했는데, 파이썬은 JS를 보지 않으니 당연한 결과였다. 그 커밋에 나는 "검증했다"고 적었지만 수치는 적이 아직 hero이던 이전 빌드에서 잰 것이었다. 다시 재 보니 "공격 락 448ms"는 실제로 480ms였고 나머지 4개는 맞았다. 하나가 틀린 것보다 네 개가 맞았다는 쪽이 더 위험했다. 전부 맞았다면 아무도 다시 보지 않았을 테니까.

지금은 빌드가 `node --check`를 돌리고, 손으로 적던 수치는 스모크가 매번 재서 출력한다.

### 스텁이 브라우저보다 관대했다

`E.rect(0, 0, VW, VH, 'rgba')`는 유효한 CSS 색이 아니다. 브라우저는 무효한 `fillStyle` 대입을 무시하고 직전 값을 유지하는데, 그게 HUD 점수의 노란색이라 타이틀·강화·사망 화면 전체가 노란 단색이 됐다. 그런데도 스모크는 전부 초록이었다. `raster.js`는 `'rgba'.slice(1,3)`을 NaN으로, 다시 0으로 읽어서 검정을 칠했다. 헤드리스와 브라우저가 서로 다른 색을 보고 있었던 셈이고, 렌더 해시도 민감도 6종도 이 차이는 볼 수 없었다.

```js
set fillStyle(v) {
  // **무효한 색을 조용히 삼키지 않는다.** 브라우저는 무효한 fillStyle 대입을 무시하고
  // ... 생략
  if (!m) throw new Error(`fillStyle 이 #rgb/#rrggbb 가 아니다: ${JSON.stringify(v)}`);
```

지금 래스터라이저는 `#rgb`/`#rrggbb`가 아니면 예외를 던진다. 이걸 붙이자마자 내 테스트 코드의 `#000`부터 잡혔다.

### 적은 바닥과 대비돼야 한다

원거리 적 셰이드를 탁한 초록으로 칠하면서 다른 적과 안 겹치는지만 봤다(slime 파랑, bat 보라, tyrant 빨강). 정작 `terrain.hex`와 대 보니 여섯 색 중 넷이 글자 그대로 같아서 풀밭에서는 윤곽선 말고 아무것도 안 보였다. 그 뒤로 "적 팔레트는 지형과 아웃라인 말고는 겹치지 않는다"를 테스트로 내렸다. 지금은 적 16종 모두 지형과 공유하는 색이 아웃라인 1개 이하다. 플레이어 팔레트는 재기만 하고 강제하지는 않는다(hero 3, blue 3, green 5색 공유). 캐릭터 색은 고르는 사람이 정할 몫으로 남겨 뒀다.

### 렉의 원인은 히트스톱이었다

맞힐 때마다 30~70ms씩 판을 세우는 히트스톱을 자동 무기·가시밭·폭발까지 걸어 놨더니, 적이 많으면 프레임의 31%가 멈춰 있었고 게임 시간은 실제의 68%로 흘렀다. 연산은 한 프레임에 2ms로 멀쩡했다. 지금은 직접 휘두른 공격, 내가 맞음, 보스 처치에서만 판을 세우고 타격 사이에는 간격을 둔다. 그렇게 바꾸니 멈춘 비율이 5%로 줄었다.

히트스톱은 연출 토글(`?fx=0`)과도 엮여 있었다. 처음엔 히트스톱까지 그 토글에 묶어 두고 "켬/끔 결과가 같다"고 적었는데, 재 보니 켬 6239점, 끔 6227점으로 달랐다. 히트스톱은 `dt`를 0으로 만들어 시뮬레이션 시간 자체를 멈추기 때문에 정의상 판정에 영향을 줄 수밖에 없다. 그래서 히트스톱을 연출 토글에서 떼어 게임 규칙 쪽으로 옮겼고, 지금은 테스트가 한 프로세스 안에서 켬/끔 플레이 궤적 28개 표본을 직접 비교한다.

## 9. 한계와 다음 단계

- 앞 행을 베끼다 같은 오타가 2행 이상 이어지는 연속 오타는 못 잡는다. 평탄 구간에서는 국소 극값이 사라지기 때문이고, 지금은 `fx-plateau.pixa`로 한계를 고정만 해 뒀다.
- 실루엣이 보존되는 내부 1px 오류(벨트 한 칸 밀림 등)는 어떤 규칙으로도 못 잡아서 8x PNG를 눈으로 보는 수밖에 없다.
- 지금 `.pixa` 79개를 전부 빌드하면 75개가 ERROR 0 / WARN 0이고, 아이콘 3개(aura, bow, ruler)와 든 활 1개에 실루엣 WARN(6·7)이 남아 있다.
- 휘도 인접 규칙은 hero에서만, 실루엣 내부 규칙(WARN 7)은 8종에서만 발화할 수 있다. 나머지 에셋에서 나온 WARN 0을 그 규칙이 지켜본 결과로 읽으면 안 된다.
- 생성기와 검사기가 같은 술어를 쓰는 탓에, `lint_outline`은 저작 스크립트를 거친 스프라이트의 캔버스 안쪽에서 발화할 수 없다.
- 슬라임 셰이딩은 구 모델을 쓰지 않는다. 광원점까지의 2D 거리에 깊이 항이 없다 보니 늘어난 hop 프레임(21×38)은 27행이 아직 가로 한 줄 밴드로 남고, 가장 어두운 색이 실루엣 끝에 붙는다.
- walk의 두 passing 프레임은 13px 차이지만 8x 육안으로는 구별하기 어렵다. 망토·후드의 follow-through도 없다.
- 술사(hero-green)의 망토가 풀과 두 색(`6abe30`, `99e550`)을 공유한다. 플레이어 팔레트는 재기만 하고 강제하지 않기로 했으니 그대로 뒀다.
- 에셋 검증 데모 맵은 47타일 중 13종만 쓰고, 나머지 34종은 카탈로그 맵과 경계 상태 테스트로만 검증한다.

손으로 쓴 격자가 형태를 지킨다는 가설은 첫날 확인했다. 그 뒤로 시간을 가장 많이 쓴 곳은 그림보다 검사 쪽이었다. 규칙이 0건을 보고해도 알고 보면 게이트 뒤에 숨어 있었거나, 생성기가 무력화했거나, 스텁이 관대해서 나온 0건인 경우가 계속 나왔다. 그래서 규칙마다 실제로 발화할 수 있는 범위를 테스트가 출력하게 했고, 완화 선언에는 하나하나 상한과 고정 목록을 붙였다.
