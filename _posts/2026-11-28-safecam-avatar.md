CCTV 4대로 공사 현장을 모델링하고 작업자의 위치와 자세를 복원해 안전 알림을 주는 시스템을 참고해, 개인 장비만으로 다시 만들어 봤다. 고정해 둔 카메라 한 대(웹캠 또는 아이폰)가 사람을 찾아 안전모를 썼는지 보고, 바닥 위 위치를 미터 단위로 계산해 위험구역에 들어서면 알린다. 작업자는 자세를 그대로 따라 하는 SMPL-X 3D 아바타로 웹 대시보드에 나타나고, 알림은 폰 푸시로도 온다. 아래 숫자는 이 PC에서 직접 잰 값이다.

| 항목 | 값 |
|---|---|
| 입력 | 노트북 웹캠, 또는 아이폰 17(LiDAR 없음)을 USB 가상 웹캠이나 Wi-Fi 스트림으로 |
| 장비 | Windows 11, RTX 4050 Laptop(VRAM 6GB) |
| 스택 | Python 3.11(uv), PyTorch CUDA 12.8, FastAPI + WebSocket, TypeScript + three.js |
| 안전모 모델 | YOLO26s, 테스트 2,685장에서 helmet mAP50 0.943, head 0.929, 1280×720 한 장 13ms(p50) |
| 자세 모델 | NLF-S(SMPL-X 127관절). 단독 측정 1명 15.3fps, 서버에서는 4~13fps |
| 화면 지연 | 카메라에서 브라우저까지 p50 약 130ms, p95 약 235ms |
| 영상과 아바타 시점 차이 | p95 1.9프레임 |
| 테스트 | Python 309개 통과(알려진 한계 4개는 xfail로 기록), 웹 37개 |
| 확인하지 못한 것 | 아이폰 Wi-Fi 스트림 종단 연결, 실제 방 스캔 정렬 |

## 1. 전체 흐름

```
카메라 ─▶ 캡처·왜곡 보정 ─▶ 사람 탐지(YOLO26s)·추적(BoT-SORT) ─▶ 안전모 판정(상태 머신)
                                  │                               └▶ 발 위치(바닥 좌표) ─▶ 위험구역
                                  └▶ 자세 추정(NLF, SMPL-X) ─▶ 아바타 ─▶ 웹(영상, 3D, 평면도, 알림)
```

처리는 세 갈래로 나뉜다. 캡처 스레드는 가장 최근 프레임만 남기고, 탐지 스레드는 사람과 머리를 찾아 안전모와 위치를 판정하고, 자세 스레드는 그중 큰 사람 세 명의 자세를 따로 추정한다. 자세 추정이 탐지보다 느리기 때문에, 두 결과를 프레임 번호로 다시 맞춰 화면에 보낸다.

준비물이 빠져도 서버는 뜬다. 렌즈 보정이 없으면 70° 화각을 가정하고, 바닥 보정이 없으면 위치와 위험구역과 아바타가 꺼지고, 안전모 모델이 없으면 안전모 판정이 꺼진다. 꺼진 기능은 로그와 화면 상태줄에 나온다.

## 2. 영상 받기

웹캠은 `cam:0?w=1280&h=720` 같은 주소로 바로 쓴다. 아이폰은 두 길을 만들었다.

- USB: 아이폰 앱이 PC에 가상 웹캠으로 잡히게 하고 웹캠처럼 읽는다. 충전 전용 케이블로는 데이터가 안 지나가서 안 된다.
- Wi-Fi: 아이폰의 Larix Broadcaster가 SRT로 PC의 MediaMTX에 보내고, 서버는 그걸 같은 PC 안에서 RTSP로 읽는다. SRT에는 암호를 걸었고, 이미 보내는 중인 폰을 다른 기기가 밀어낼 수 없게 했다. RTSP는 이 PC 밖으로 열지 않는다.

캡처는 끊기면 다시 붙는다. 처음에는 카메라가 보정 때와 다른 해상도로 보내도 그냥 "신호 없음"으로만 보였는데, 지금은 "해상도 불일치 1920×1080 (보정 1280×720)"처럼 원인을 상태줄에 띄운다.

## 3. 안전모 판정

### 데이터와 학습

사람 탐지는 사전학습 YOLO26s를 그대로 쓰고, 머리를 `helmet`과 `head`(맨머리) 두 클래스로 찾는 모델만 따로 학습했다. 데이터는 Roboflow Universe의 Hard Hats(CC BY 4.0, Hugging Face 미러 약 1.97만 장)와 SHWD(MIT)를 합쳤다.

처음 나눈 데이터에서는 학습과 테스트 사이에 거의 같은 사진이 112장 섞여 있었다. 같은 원본에서 증강으로 만든 사진들이 서로 다른 쪽에 들어간 것이다. 그래서 출처끼리 겹치는 사진 485장을 지각 해시(pHash)로 지우고, 원본 이름과 pHash 거리 4 이하로 묶은 그룹 단위로 나눴다. 다시 나눈 뒤에는 테스트와 학습 사이의 근접 사본이 0장이다.

80 epoch 계획은 이 노트북에서 약 24시간이 걸려서 30 epoch(조기 종료 15)로 줄였다. batch 16은 VRAM 6GB를 넘어 공유 메모리로 밀리면서 7배 느려져서 12로 돌렸다.

| 클래스 | mAP50 (테스트 2,685장) |
|---|---|
| helmet | 0.943 |
| head | 0.929 |
| 전체 mAP50-95 | 0.543 |

목표는 두 클래스 모두 mAP50 0.85 이상이었다. 다만 이 점수는 인터넷에서 모은 현장 사진 기준이고, 실제 웹캠과 아이폰 화면에서 안전모를 썼다 벗었다 하며 잰 알림 평가는 아직 하지 않았다.

### 한 프레임이 아니라 시간으로 판정

머리 모델이 한 프레임 틀렸다고 알림을 보내면 안 된다. 사람마다 상태 머신을 두고 최근 1.5초의 판정을 모아 본다.

| 단계 | 조건 |
|---|---|
| 판정 가능 | 1.5초 창 안에서 머리 모델이 실제로 돈 횟수의 40% 이상에 머리 판정이 있음 |
| 확인 중(WARN) | 맨머리 비율 70% 이상 |
| 알림(ALERT) | WARN이 1.5초 이어짐. 같은 사람에게는 30초 뒤에 다시 알림 |
| 해제 | 안전모 비율 80% 이상 |
| 확인 불가 | 5초 동안 머리를 판정할 수 없음(가려짐, 뒤돈 자세) |

### 알림이 1,626번 울린 이유

약 20시간을 켜 두고 기록을 보니 안전모 알림이 1,626건, 서로 다른 사람 번호가 538개였다. 재알림 대기(30초)가 사람 번호마다 따로 돌았는데, 추적기는 사람이 잠깐 가려지면 새 번호를 준다. 번호를 이어 주는 기능은 발이 보여야 동작해서, 발이 거의 안 보이는 노트북 웹캠에서는 사실상 꺼져 있었다.

고친 방식은 이렇다.

- 사람이 사라진 자리 근처(박스 높이의 절반 안)에서 6초 안에 새 번호가 잡히면, 알림을 받은 적이 있는 쪽의 재알림 대기를 이어받는다.
- 원래 번호가 다시 보이면 옆사람이었던 것이므로 이어받기를 취소한다. 한 프레임만 놓친 옆사람에게 대기를 넘기는 경우를 평가 단계에서 찾아 막았다.
- 폰 푸시는 1분에 한 번까지 보내고, 그사이 생긴 알림은 "알림 N건"으로 묶는다. 하루(UTC)에 200건이 넘으면 멈춘다.

걷던 사람이 가려졌다가 박스 높이의 절반 넘게 떨어진 곳에서 새 번호로 잡히면 아직 이어받지 못한다. 그 경우의 소음은 푸시 묶음이 줄인다.

## 4. 바닥 위 위치와 위험구역

화면 속 발 위치를 바닥 좌표(미터)로 바꾸려면 카메라가 바닥을 어떻게 보는지 알아야 한다. 두 가지 보정을 만들었다.

- 줄자 보정: ChArUco 보드를 인쇄해 렌즈를 보정하고, 바닥에 테이프로 찍은 점의 좌표를 줄자로 재서 solvePnP로 카메라 자세를 구한다.
- 자동 보정: MoGe-2가 사진 한 장에서 예측한 거리와 면의 방향으로 위쪽 방향과 카메라 높이를 구한다. 줄자가 필요 없다.

자동 보정에서 재미있는 문제가 나왔다. 처음 방식은 "카메라가 대략 똑바로 서 있다"에서 출발해 그 근처의 수평면만 찾았는데, CCTV처럼 35° 넘게 숙이면 바닥을 못 찾거나 앞 벽을 바닥으로 읽었다. "바닥이 화면 아래쪽에 있다"는 단서로 바꾸자 이번에는 노트북 웹캠(위로 약 30° 올려다봄)에서 사람 얼굴을 바닥으로 읽었다.

결국 깊이 지도 한 장으로는 "아래로 바닥과 앞 벽을 본 장면"과 "위로 천장과 앞 벽을 본 장면"이 거울상이라 구분되지 않는다는 결론이 났다. 그래서 설치 방식을 사람이 알려 주게 했다.

| `--view` | 카메라 | 판정 규칙 |
|---|---|---|
| `down` | 바닥을 내려다봄(5~85°, 높이 단 CCTV) | 위를 향한 면 중 화면에서 가장 아래 있는 것이 바닥. 카메라가 위를 보는 해석은 버린다 |
| `level` | 거의 수평(±30°, 위로 볼 수도 있음) | 똑바로 선 카메라에서 출발해 수평면을 찾는다 |
| `overhead` | 천장에서 거의 수직(70~90°) | 렌즈를 정면으로 보는 큰 평면이 바닥 |

그리고 결과의 기울기와 카메라 높이가 적은 `--view`와 맞지 않으면 저장하지 않는다. `down`인데 카메라가 위를 보거나, 높이가 1.8~6m 밖이면 거부한다. 다만 `--view`를 잘못 적었는데 결과가 우연히 그럴듯하면 막지 못한다. 노트북을 `down`으로 돌렸는데 앞 벽까지가 3~5m면 벽까지 거리가 카메라 높이로 나온다. 이 경우는 테스트에 알려진 한계(xfail)로 남겨 뒀고, 도구가 출력하는 기울기를 사람이 확인하게 했다.

위험구역은 바닥 좌표로 그린 다각형이다. 발 위치가 0.3초 이어서 안에 있으면 진입, 0.5초 이어서 밖에 있으면 이탈로 본다. 발이 화면 아래로 잘려 위치를 모르면 구역 타이머는 멈춘다.

## 5. 자세를 따라 하는 3D 아바타

자세는 NLF-S로 SMPL-X 파라미터를 추정한다. 단독으로 재면 1명 15.3fps(3회 중앙값), VRAM 1.1~1.8GB였다. 서버에서 탐지와 함께 돌리면 4~13fps로 흔들리고, 화면 속 사람이 많을 때 떨어진다. 목표였던 10fps를 못 넘는 구간이 있다.

아바타를 자연스럽게 보이게 하려고 몇 가지를 했다.

- 관절 회전은 One Euro 필터로 떨림을 줄이고, 몸 전체의 가장 낮은 정점을 바닥(z=0)에 둔다. 앉거나 무릎을 꿇어도 바닥을 뚫지 않는다.
- 자세 추정 사이에는 몸 모양은 그대로 두고 바닥 위치만 탐지 결과를 따라 옮긴다.
- 발이 안 보이면 자세 모델이 스스로 추정한 깊이로 세운다. 위험구역 판정에는 이 값을 쓰지 않는다.
- 자세가 1초 넘게 갱신되지 않으면 아바타를 숨긴다. 처음에는 자세 모델이 건너뛴 사람(큰 순서로 3명 밖)의 마지막 자세가 계속 남아서, 영상과 아바타의 시점 차이가 p95 341프레임까지 벌어졌다. 지금은 1.9프레임이다.

## 6. 대시보드

서버는 FastAPI다. 매 프레임 사람별 상태를 JSON으로, 아바타 메시는 정점 10,475개를 float16 바이너리로 WebSocket에 보낸다. 영상은 MJPEG로 따로 보내는데, 브라우저가 MJPEG를 직접 파싱해 지금 화면에 그린 프레임의 번호를 안다. 그래서 "보이는 영상"과 "보이는 아바타"의 시점 차이를 실제로 잴 수 있다.

화면은 영상, 3D 공간, 위에서 본 평면도, 알림 목록이다. 평가에서 지적받아 바꾼 것이 둘 있다.

- 브라우저가 밀릴 때: 예전에는 메시지마다 화면 전체를 두 번씩 다시 그렸다. 지금은 화면 한 프레임에 가장 최근 스냅샷과 메시만 그리고, 건너뛴 스냅샷의 이벤트는 이어 붙인다. 탭이 숨겨져 있다 돌아와도 밀린 메시지를 따라잡느라 멈추지 않는다.
- "실시간"이라는 표시를 믿을 수 있게: 예전에는 메시지가 도착한 시각만 봐서, 38초 전 데이터도 계속 도착하면 실시간처럼 보였다. 지금은 `/api/time`으로 서버 시계와의 차이를 재고(왕복이 가장 짧은 샘플), 캡처한 지 1.5초가 넘은 데이터면 "늦게 들어옴"으로 표시한다. 폰처럼 시계가 몇 초 다른 기기에서도 맞게 나온다.

보정 상태도 정직하게 바꿨다. 예전에는 바닥을 못 본 자동 보정도 "완료"로 나왔다. 지금은 줄자, 자동, 추정값(바닥 안 보임), 다른 카메라 보정값으로 나눠 보여 준다. 보정 파일에는 어떤 카메라로 보정했는지 기록해서, 다른 카메라로 켜면 그 보정을 쓰지 않는다.

## 7. 폰으로 보기와 알림

- `--lan`: 같은 Wi-Fi의 폰에서 대시보드를 연다. 이 PC에서는 키 없이 열리고, 다른 기기는 시작할 때 출력되는 주소의 접근 키(`?k=`)로 한 번 들어오면 HttpOnly 쿠키로 이어진다. 키가 없으면 영상 스트림과 WebSocket까지 모두 거부한다.
- `--ntfy`: ntfy 공개 서버로 "#3 안전모 미착용" 같은 문구만 보낸다. 사진은 보내지 않는다. 토픽 이름이 곧 비밀번호라 처음 실행할 때 추측하기 어려운 이름을 만든다.

기관 Wi-Fi는 기기끼리 통신을 막는 경우가 많아서, 그때는 PC를 아이폰 개인용 핫스팟에 붙이면 된다.

## 8. 공간 스캔 정렬(선택)

아이폰으로 방을 스캔한 PLY를 3D 화면 배경으로 쓸 수 있게, 카메라 자동 보정이 만든 점구름에 스캔을 자동으로 맞추는 도구를 만들었다. 스캔이 중력 방향의 축 하나와 맞는다는 점을 이용해 위쪽 축 6가지 × 방향 10° 간격 × 배율 후보마다 FFT로 가장 많이 겹치는 위치를 찾고, 상위 후보를 배율까지 맞추는 ICP로 다듬는다.

빈 방처럼 위치가 하나로 정해지지 않는 장면이 문제였다. 처음 버전은 벽과 바닥만 보이는 장면에서 5m 틀린 정렬을 통과시켰다. 지금은 카메라가 본 빈 공간에 스캔이 들어가 있는지 검사하고, 찾은 위치를 0.5m씩 밀었다가 다시 맞춰 봐서 다른 곳에 똑같이 잘 맞으면 "모호"로 거부한다. 합성한 방 6가지는 1.2~1.8cm로 맞췄고 빈 방 세 가지는 모두 거부됐다. 실제 스캔으로는 아직 해 보지 않았다.

## 9. 만든 방식

구현은 Claude Code로 했다. 단계(Stage 0~6, 폰 연동, 평가 후속 수정)를 나누고, 단계가 끝날 때마다 만든 쪽과 다른 세션의 평가 에이전트가 코드를 처음부터 읽고 위험, 보통, 통과로 판정했다. 통과해야 다음 단계로 넘어갔다.

마지막으로 전체를 다시 평가받았을 때는 "보통"이었고, 이 글의 3~6절에 적은 문제들이 그때 나왔다. 그 수정도 같은 방식으로 했다.

| 수정 단계 | 처음 판정 | 막힌 이유 | 최종 |
|---|---|---|---|
| 알림 폭주 | 보통 | 한 프레임 놓친 옆사람에게 대기가 넘어감, 출입구로 나중에 온 사람도 이어받음, 하루 한도를 로컬 날짜로 셈 | 통과 |
| 자동 보정 | 위험 → 보통 | 카메라를 단 벽을 바닥으로 읽음, 거의 수평인 카메라가 앞 벽을 바닥으로 읽음 | 통과 |
| 아바타와 실시간 표시 | 보통 | 묶음 처리에서 오래된 메시가 숨긴 아바타를 되살림, 숨긴 탭에서 이벤트가 끝없이 쌓임 | 통과 |
| 견고성 | 보통 | 같은 카메라를 주소 표기만 보고 다른 카메라로 판정, 사진 정리가 안전 판정 스레드를 최대 0.9초 멈춤 | 통과 |

## 10. 한계

- 자세 추정이 사람 수와 부하에 따라 4~13fps로 흔들리고, 10fps를 못 넘는 구간이 있다.
- 안전모 점수는 인터넷 사진 기준이다. 실제 카메라로 안전모를 썼다 벗었다 하며 잰 알림 오탐과 지연은 아직 없다.
- 아이폰 Wi-Fi 스트림은 설정과 테스트까지만 했고, 실제 폰에서 끝까지 연결해 보지 않았다.
- 공간 스캔 정렬은 합성 데이터로만 확인했다.
- 자동 보정은 `--view`를 잘못 적었을 때 그럴듯한 오답을 다 막지 못한다.
- 카메라 한 대가 보는 범위만 다룬다. 여러 대를 이어 삼각측량하는 것은 범위 밖이다.
