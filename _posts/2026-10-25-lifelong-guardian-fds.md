## 1. 문제: 300만원은 위험한 금액인가

고정 금액 룰은 "65세 이상이 100만원 넘게 보내면 경고" 같은 식이다. 그런데 매달 아들에게 생활비를 보내고 가끔 250만, 300만원도 보내던 어르신에게 300만원은 평소 거래다. 반대로 20만원대만 보내던 어르신이 처음 보는 '안전계좌'로 300만원을 보내면 금액보다 그 이탈 자체가 신호다.

그래서 거래 한 건을 이런 입력으로 받는다.

| 필드 | 의미 | 데모 | 실서비스 가정 |
|---|---|---|---|
| `amount` | 이체 금액 | 슬라이더 / 시나리오 | 거래 이벤트 |
| `age` | 고객 연령 | 페르소나 | 고객 정보 |
| `isNew` | 신규 수취인 여부 | 페르소나 | 수취인 이력 |
| `known` | 평소 거래하던 상대인지 | 페르소나 | 거래 이력 |
| `baseAmounts` | 과거 이체 금액들 | 합성 5~6건 | 자행 거래내역 |
| `usualHours` | 평소 거래 시간대 | 합성 | 자행 거래내역 |
| `hour` | 이번 거래 시각 | 시나리오 | 거래 이벤트 |
| `account` | 수취계좌 | 시나리오 | 거래 이벤트 |

데모의 거래 이력은 전부 합성이고 등장인물은 실존 인물이 아닌 페르소나다. 사기 방어 시나리오의 김OO(재생 화면 속 이름은 김순자)와 박OO 두 명, 실시간 감시 탭의 가상 고객 다섯 명이 따로 있다. 감시 탭에도 김순자라는 고객이 있지만 과거 이체가 15만~20만원인 별개 페르소나다. 실서비스라면 은행이 이미 가진 자행 거래내역으로 `baseAmounts`와 `usualHours`를 채우게 된다.

## 2. 3층 엔진

{% include embed/video.html src='/assets/img/posts/lifelong-guardian-fds/explainer.mp4' poster='/assets/img/posts/lifelong-guardian-fds/explainer-poster.jpg' title='김OO 시나리오(백엔드 켬)의 이체 한 건이 1층 룰, 2층 z-score 베이스라인, 3층 계좌평판을 지나 송금 보류와 ARS·지정인 알림까지 가는 과정' loop=true %}

엔진은 `backend/fds.py`의 `evaluate()` 하나다. 데모 HTML 안에도 같은 함수를 JS로 두고, 파이썬 쪽은 그걸 1:1로 포팅했다. 백엔드가 꺼져 있어도 데모가 같은 판정을 내게 하려는 구조다.

| 층 | 신호 | 가중치 |
|---|---|---|
| 1층 룰 | 65세 이상 + 신규 수취인 + 100만원 이상 | +50 |
| 1층 룰 | 0~6시 거래 | +20 |
| 2층 베이스라인 | 처음 보는 수취인 | +25 |
| 2층 베이스라인 | 금액 z ≥ 3 | +35 |
| 2층 베이스라인 | 평소 거래 시간대가 아님 | +15 |
| 3층 평판 | 사기 신고 이력 계좌 | 점수 무시, 즉시 100점 차단 |

가중치(50/35/25/20/15)와 임계값(35/70, z ≥ 3)은 2024 FDS 가이드라인이 강조하는 고령·신규 수취인·고액·심야 항목을 기준으로 내가 손으로 정했고 데이터로 학습한 값은 없다.

### 1층: 가이드라인 룰

```python
# ── 1층: FDS 가이드라인 룰 ──
if age >= 65 and is_new and amount >= 1_000_000:
    flags.append({"layer": 1,
                  "text": f"고령 계좌 → 신규 수취인에게 {won(amount)}원 (100만원↑)", "pts": 50})
if hour < 6:
    flags.append({"layer": 1, "text": "심야(0~6시) 시간대 거래", "pts": 20})
```

개인화와 무관하게 누구에게나 같은 기준이다. 차단 사유를 사람이 바로 읽을 수 있어서 설명용 신호로도 쓴다.

### 2층: 이 사람의 평소 대비 이탈

```python
# ── 2층: 개인화 베이스라인 이탈 ──
if not known:
    flags.append({"layer": 2, "text": "평생 처음 보는 수취인", "pts": 25})
if base_amounts:
    m = _mean(base_amounts)
    sd = _pstd(base_amounts)
    z = (amount - m) / sd
    if z >= 3:
        flags.append({"layer": 2,
                      "text": f"평소(약 {won(round(m))}원)보다 비정상적으로 큰 금액 (z={z:.1f})",
                      "pts": 35})
else:
    m = amount
if hour not in usual_hours:
    flags.append({"layer": 2, "text": "평소 거래하지 않던 시간대", "pts": 15})
```

금액 이탈은 고객 본인의 과거 이체액으로 계산한 z-score다.

$$
z = \frac{x - \mu}{\sigma}, \qquad \sigma = \sqrt{\frac{1}{n}\sum_{i=1}^{n}(x_i - \mu)^2}
$$

표본표준편차가 아니라 모표준편차를 쓴다. JS 쪽 `pstd`와 결과를 맞추기 위해서다. 과거 이체가 전부 같은 금액이라 σ가 0이 되는 경우는 1로 바꿔 0으로 나누기를 막는다.

```python
def _pstd(a):
    """모표준편차. JS의 `... || 1`처럼 0이면 1로 보정(0으로 나눔 방지)."""
    m = _mean(a)
    v = sum((x - m) ** 2 for x in a) / len(a)
    return math.sqrt(v) or 1.0
```

### 합산과 신호등

```python
score = min(100, sum(f["pts"] for f in flags))
if score >= 70:
    level, cls, action = "위험 🔴", "danger", "stop"
elif score >= 35:
    level, cls, action = "주의 🟡", "warn", "warn"
else:
    level, cls, action = "안전 🟢", "safe", "go"
```

`say` 안내 문구 분기는 생략했다. 위험이면 송금을 멈추고, 주의면 한 번 더 확인을 받고, 안전이면 그대로 보낸다.

### 3층: 수취계좌 평판

점수와 별개로 받는 계좌가 사기 신고 이력 계좌면 무조건 막는다. 이 층은 `/fds` 엔드포인트에서 `evaluate()` 결과 위에 덮어쓴다.

```python
res = fds.evaluate(inp.age, inp.isNew, inp.known, inp.amount,
                   inp.baseAmounts, inp.usualHours, inp.hour)
# 수취계좌 평판: 사기 신고 이력 계좌면 점수 무시하고 '완전 차단'
if inp.account and reputation.is_fraud(inp.account):
    res["flags"].insert(0, {"layer": "평판",
                            "text": "사기 신고 이력이 있는 계좌 (수취계좌 평판 조회)", "pts": 100})
    res.update(score=100, level="위험 🔴", cls="danger", action="stop", blacklisted=True,
               say="이 계좌는 사기 신고 이력이 있어요. 절대 보내면 안 됩니다. 송금을 멈췄습니다.")
```

계좌 문자열은 `re.sub(r"\D", "", a)`로 숫자만 남겨 비교한다. "○○은행 901-2345-0021"처럼 은행명과 하이픈이 섞여 들어와도 같은 계좌로 잡힌다.

블랙리스트는 `fraud_accounts.json`의 샘플 4건이다. 공공데이터의 우체국 사기계좌 정보에는 계좌번호가 없어서 실명단을 구할 방법이 없었다. 실서비스라면 이 자리에 은행권 사기이용계좌 공유 DB나 더치트 API를 붙여야 한다. 그리고 이 층은 백엔드에만 있다. 브라우저 안의 JS 엔진은 1·2층까지만 계산한다.

## 3. 같은 300만원 검산

데모 프리셋 두 개를 그대로 넣고 손으로 계산해 봤다.

| | 박OO (아들 송금) | 김OO (검찰 사칭) |
|---|---|---|
| 나이 / 신규 / 아는 상대 | 71 / 아니오 / 예 | 73 / 예 / 아니오 |
| 과거 이체 | 30만, 35만, 28만, 250만, 300만, 32만 | 20만, 25만, 18만, 30만, 22만 |
| 평소 시간대 / 이번 | 10·11·14·15시 / 14시 | 9·10·13·16시 / 14시 |
| μ | 1,125,000 | 230,000 |
| σ | 1,158,271 | 41,952 |
| z (300만) | 1.62 | 66.03 |
| z = 3이 되는 금액 | 4,599,813 | 355,857 |

김OO의 σ는 편차 제곱합이 $(-3)^2+2^2+(-5)^2+7^2+(-1)^2 = 88$ (단위 만원²)이라 $\sqrt{88/5} \approx 4.195$만원이고, $z = (300 - 23)/4.195 = 66.03$이다. 점수는 이렇게 쌓인다.

| 신호 | 박OO | 김OO |
|---|---|---|
| 1층 고령·신규·100만↑ | 0 | +50 |
| 2층 처음 보는 수취인 | 0 | +25 |
| 2층 z ≥ 3 | 0 (z=1.6) | +35 (z=66.0) |
| 2층 평소 시간대 아님 | 0 | +15 |
| 합계 → 판정 | 0 → 안전 | 125 → 100으로 자름 → 위험 |

| 받는 사람 | 평소 패턴 | 신호 | 점수 | 판정 |
|---|---|---|---|---|

| 처음 보는 사람 | 소액만 | +50, +25, z +35 | 100 | 위험 |

## 4. 가중치가 만든 경계들

전부 손으로 정한 가중치라서 조합별로 어디서 판정이 갈리는지 직접 돌려 보면 설계 문서에 없던 성질이 몇 개 보인다.

- 금액 이탈 하나로는 막지 않는다. z가 아무리 커도 +35라서 혼자서는 주의까지만 간다. 아는 사람에게 평소보다 훨씬 큰 돈을 보내는 건 한 번 더 확인하는 선에서 끝낸다. 차단까지 가려면 수취인이나 시간대 신호가 같이 있어야 한다.
- 100만원에 절벽이 있다. 처음 보는 사람에게 소액 패턴 고객이 낮에 99만원을 보내면 25 + 35 = 60점으로 주의, 100만원이면 1층 50점이 더해져 100점 위험이다. 1층 조건이 계단 함수라서 생기는 일이다.
- 65세 이상이 100만원 이상을 보낼 때는 신규 수취인이 두 번 세진다. `isNew`(1층)와 `known`(2층)은 입력이 따로지만 데모의 모든 프리셋에서 `isNew = !known`이다. 이 조건에서는 같은 사실 하나가 50 + 25 = 75점을 만들고 그것만으로 위험 임계 70을 넘는다. 실서비스라면 "최근 등록 수취인"과 "거래한 적 없는 수취인"처럼 두 신호의 정의를 실제로 갈라야 의미가 있다.
- 큰 이체 한두 번이 σ를 부풀린다. 박OO은 30만원 안팎 4건과 250만·300만 2건이 섞인 두 덩어리 분포라 σ가 평균보다 크다. 그 결과 z = 3 경계가 460만원까지 올라간다. 평소 30만원씩 보내던 패턴인데도 460만원 직전까지는 금액 신호가 안 뜬다. 중앙값·MAD 같은 robust 통계나 수취인별 베이스라인이 필요하다.
- 위쪽 이탈만 본다. `z >= 3`만 검사하니 평소보다 작은 금액은 신호가 없다. 사기 피해 시나리오만 보면 맞지만 쪼개기 송금처럼 작은 금액을 여러 번 보내는 패턴은 2층이 못 잡는다.

## 5. 실시간 감시 탭의 과차단

데모의 "실시간 감시" 탭은 고객 5명의 가상 거래를 1.5초마다 만들어 같은 `evaluate()`에 넣는다. 공격 거래는 처음 보는 계좌로 200만~350만원이라 1층과 처음 보는 수취인만으로 75점 이상, 항상 위험이다. 문제는 정상 거래였다. 처음 버전은 이랬다.

```js
const amt=Math.round(m*(0.8+Math.random()*0.5)/10000)*10000;
// ... 생략
const r=evaluate(tx.u,tx.amount),blocked=r.cls!=='safe';
```

정상 거래 금액은 과거 이체 중 하나를 골라 0.80~1.30배를 곱하고 만원 단위로 반올림했다. 평소 금액에 이 정도 변동이 붙으면 z가 3을 넘을 수 있고 주의(35점)까지 전부 "자동 차단"으로 표시했다. 정상 거래가 과하게 차단돼서 배수를 0.85~1.10으로 좁히고 판정 분기를 이렇게 고쳤다.

```js
const amt=Math.round(m*(0.85+Math.random()*0.25)/10000)*10000;
// ... 생략
const r=evaluate(tx.u,tx.amount),blocked=r.cls==='danger',warned=r.cls==='warn';
```

자동 차단은 위험만, 주의는 "확인 요청"으로 분리했고 공격 비율도 28%에서 22%로 낮췄다. 수정 전후에 정상 거래가 z ≥ 3에 걸리는 비율을 고객별로 다시 계산해 보면 원인이 분명하다. 아래 값은 데모의 생성식을 그대로 따라 평소액 하나를 고르고 배수를 균등하게 촘촘히 훑어 낸 비율이다.

![정상 거래가 z ≥ 3에 걸리는 비율](/assets/img/posts/lifelong-guardian-fds/monitor-fp-light.png){: .light }
![정상 거래가 z ≥ 3에 걸리는 비율](/assets/img/posts/lifelong-guardian-fds/monitor-fp-dark.png){: .dark }
_σ가 작은 고객일수록 평소 금액의 10~30% 변동만으로 z가 3을 넘는다_

차트의 다섯 명은 감시 탭의 가상 고객이다. 여기의 김순자는 과거 이체 15만~20만원인 감시 탭 고객이고, 3절 김OO 시나리오와는 다른 데이터다.

정복동 고객은 과거 이체가 48만~52만원이라 σ가 14,790원이다. 52만원에 1.1을 곱해 만원 단위로 반올림한 57만원만 보내도 $z = (570{,}000 - 502{,}500)/14{,}790 = 4.6$이 된다. 수정 후에도 정상 거래의 9.3%가 주의로 뜬다. 박영수 고객은 σ가 107만원이라 0%다.

이 수정은 엔진은 그대로 두고 시뮬레이터의 변동 폭만 줄였다. 과거 이체 4건으로 σ를 추정하면 금액이 일정한 고객일수록 정상적인 작은 변화에도 z가 쉽게 커진다. 실서비스에서는 σ에 하한을 두거나(예: 평균의 일정 비율), 표본 수가 적을 때 z 신호를 끄는 처리가 필요하다.

## 7. 자산 케어 RAG: CPU에서 도는 작은 구성

검색 구조는 공정위 의결서 RAG([별도 글](/posts/kftc-hybrid-rag/))와 같은 BM25 + dense + RRF지만 문서 8종짜리라 훨씬 가볍게 다시 짰다.

| 항목 | 값 |
|---|---|
| 문서 | 주택연금, 기초연금, 예금자보호, 정기예금·적금, 보이스피싱 대응, 의료비·실손, 전북은행·광주은행 시니어 예금 |
| 청크 | 빈 줄·헤딩 경계 문단, 15자 미만 제외, 37개 |
| 희소 검색 | `rank-bm25`, 정규식 단어 + 한글 2-gram (형태소 분석기 없음) |
| 밀집 검색 | Ollama `bge-m3`, L2 정규화 후 내적 |
| 융합 | RRF, k = 60, 상위 4개 |
| 생성 | Ollama `exaone3.5:2.4b`, temperature 0.2, 최대 320토큰 |
| 벡터 저장 | Qdrant 없이 인메모리 행렬 + `sha1` 키 임베딩 캐시 |

문서마다 맨 아래 `## 출처` 섹션에 인용 URL을 달아 두는데, URL 목록이 검색 결과에 끼지 않도록 색인 전에 잘라 낸다. 각 청크의 색인 텍스트에는 문서 제목과 섹션 제목을 앞에 붙여 문단만 떼어 냈을 때 사라지는 맥락을 보충했다.

```python
# '## 출처'(인용 URL 목록) 이후는 임베딩에서 제외, 검색을 오염시키지 않도록
raw = re.split(r"^#{1,6}\s*출처", raw, flags=re.M)[0]
```

### 가드레일 두 단계

```python
hits, top = self.search(query)
# 가드레일 1: 근거가 약하면 LLM을 부르지 않고 안전하게 폴백
if top < RELEVANCE_THRESHOLD:
    return {"answer": "제가 확실히 모르는 내용이에요. 가까운 영업점 상담사에게 연결해 드릴게요.",
            "sources": [], "guardrail": True}
# ... 컨텍스트 조립, 생성 생략
# 가드레일 2: 모델이 '모른다'고 답하면 출처를 붙이지 않는다
guard = "상담사에게 연결" in ans and "모르" in ans
sources = [] if guard else list(dict.fromkeys(h["title"] for h in hits))
```

첫 단계 기준으로는 dense 코사인 최댓값을 쓴다. RRF는 순위만 보니 질문과 전혀 무관한 문서도 1등은 나온다. bge-m3로 재 보니 관련 질문은 0.68~0.80, 범위 밖 질문은 0.45 근처여서 그 사이 0.55를 경계로 잡았다. 범위 밖 질문은 LLM을 아예 부르지 않으니 응답도 빠르다. 두 번째 단계는 모델이 근거 부족으로 거절했는데 출처 칩이 붙어 마치 근거가 있는 것처럼 보이는 경우를 막는다.

시스템 프롬프트는 근거 밖 내용을 금지하고, 거절 문장을 정확히 지정하고, 숫자는 근거 그대로 말하게 했다.

```python
SYSTEM_PROMPT = (
    "당신은 '평생곁에'의 금융비서입니다. 전북·전남에 사는 어르신에게 금융을 아주 쉽게 설명합니다.\n"
    "반드시 지킬 규칙:\n"
    "1) 아래 [근거] 안에 있는 내용만 사용해 답하세요. [근거]에 없는 내용은 절대 지어내지 마세요.\n"
    "2) [근거]로 답할 수 없으면 정확히 이렇게만 답하세요: "
    "'제가 확실히 모르는 내용이에요. 가까운 영업점 상담사에게 연결해 드릴게요.'\n"
    "3) 어르신이 이해하기 쉽게, 짧고 따뜻하게 3~4문장 이내로 답하세요. 어려운 용어는 풀어서 말하세요.\n"
    "4) 금액·나이·기간 같은 숫자는 [근거]에 적힌 그대로 정확히 말하세요.\n"
    "5) 사기·송금이 의심되면 단정해서 권하지 말고 멈추라고 안내하세요."
)
```

2번 규칙의 거절 문장은 가드레일 1의 폴백 문장과 똑같이 맞췄다. 그래야 가드레일 2가 문자열 검사로 거절을 알아볼 수 있다.

로컬 CPU에서 적어 둔 응답 시간은 첫 호출 약 50초(모델 로딩), 이후 0.9~1.6초, 가드레일 폴백 약 0.2초였다. 송금 차단은 LLM이 아니라 `/fds`가 하니 이 지연과 무관하다. 다만 `/fds`의 HTTP 응답 15~20ms는 측정 스크립트를 남기지 않았다. 지금 이 글을 쓰는 PC에서 판정 함수만 따로 재 보면 `evaluate()` 한 번에 약 21µs(파이썬 3.14, 10만 회 평균)라 병목은 네트워크와 프레임워크 쪽이다.

## 10. 한계와 다음 단계

- 데이터가 합성이다. 거래 이력과 페르소나는 전부 만든 값이고, 사기계좌 블랙리스트도 임의 샘플 4건이다. 실거래로 오탐률을 잰 적이 없다.
- 가중치는 손으로 정한 값이다. 실거래가 쌓이면 로지스틱 회귀처럼 데이터로 가중치를 다시 정하고, 그다음 Isolation Forest나 사기 계좌 연결망을 보는 GNN으로 넘어가는 게 계획이었다.
- 2층 통계가 취약하다. 표본 4~6건의 모표준편차, 두 덩어리 분포에서의 σ 부풀림, 위쪽 이탈만 보는 검사는 4·5절에서 본 대로다.
- 3층은 백엔드에만 있다. 브라우저 폴백 엔진은 1·2층만 계산한다.
- 채널 연동은 화면으로 재현만 했다. ARS, 알림톡, 지정인 알림의 실제 연동은 설계 단계다. 실시간 차단도 자행 이체에서만 가능하고, 타행(마이데이터)은 주기 조회라 사후 모니터링용이다.
- EXAONE-3.5는 연구·비상업 라이선스라 상용 배포라면 HyperCLOVA X 같은 상업 이용 가능 모델로 바꿔야 한다. RAG와 FDS 구조는 모델과 독립이라 교체 비용은 작다. 덧붙여 `ANTHROPIC_API_KEY`를 넣으면 생성만 Claude API로 바뀌는 옵션을 넣어 뒀는데, 이 경우는 온프레미스가 아니다.
- 고령자 사용성은 검증하지 못했다. 큰 글씨, 고대비, 읽어주기를 넣었지만 실제 고령 사용자 필드 테스트는 하지 않았고 대규모 환각률 측정도 하지 않았다.

지금 가중치 조합을 전부 돌려 보면 같은 사실이 두 번 세지고, 100만원에서 판정이 뒤집히고, σ 하나에 금액 경계가 460만원까지 밀리는 게 보인다. 룰 몇 줄짜리 엔진이라도 다음 버전은 이 조합표부터 테스트로 고정해야 한다.
