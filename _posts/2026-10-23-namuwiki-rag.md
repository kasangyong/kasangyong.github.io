## 1. 만들기 전에 잰 것들

설계 문서보다 대상 크기를 먼저 쟀다. `나무위키:통계` 페이지를 보면 문서 이름공간은 리다이렉트를 포함해 1,894,043개이고, 나무위키가 공시한 리다이렉트 비율이 34.43%이니 실질 콘텐츠 문서는 약 124만 개가 된다. 분류는 232,870개, 틀은 103,689개였다.

처음엔 문서당 HTML을 1.2MB로 잡았다. 그런데 덤프에서 무작위로 뽑은 제목 12개를 실제로 받아 보니 평균 231,926B, 중앙값 110,664B였다. 처음에 열어 본 문서들이 유명 문서 쪽으로 치우쳐 있었다. 텍스트 길이 분포도 꼬리가 길다.

재 보다가 설계를 바꾸게 된 발견이 두 가지 더 있었다.

하나는 덤프에 헤딩이 없다는 점이다. 공식 덤프는 2021-03이 마지막이다. 커뮤니티 추출본(`heegyu/namuwiki-extracted`, 565,293행)은 평문이라 쓰기는 편한데, `== 개요 ==` 같은 섹션 구분이 전부 지워져 있고 커버리지도 실질 문서의 46%에 그친다. 검색 결과에 `부산광역시 › 지리 > 도시구조 > 특징` 같은 경로를 붙이려면 헤딩이 있어야 해서 덤프는 제목 시드 565K개로만 쓰고 본문은 크롤로 받았다.

다른 하나는 `/sidebar.json`이 32초짜리 창이라는 점이다. `/RecentChanges`는 JS로 그리는 SPA라 서버 응답이 비어 있고, 같은 정보는 `/sidebar.json`이 JSON으로 준다. 문제는 항목이 15개로 고정돼 있어 약 32초만 덮는다는 것이다. 10초 간격으로 18회(198초) 폴링해 보니 고유 문서 77개가 바뀌었다. 초당 0.389개, 하루로 치면 33,600개다. 폴링 주기가 30초를 넘으면 그 사이의 편집은 다시 확인할 방법이 없어서 주기를 10초로 고정했다. 하루 8,640회라 부하는 무시할 만하다.

## 2. 단계는 Kafka 토픽으로만 대화한다

![파이프라인 구성](/assets/img/posts/namuwiki-rag/pipeline-dark.png){: .dark }
_서비스끼리 직접 호출하지 않는다. 크롤러가 수확한 링크는 crawl_state 테이블로 돌아가 프런티어가 된다_

| 토픽 | 파티션 | 정리 정책 | 용도 |
|---|---|---|---|
| `crawl.requests` | 6 | delete (7일) | 작업 큐 |
| `docs.raw` | 6 | compact, 영구 | 재파싱의 원천 |
| `chunks.ready` | 12 | compact, 영구 | 재임베딩의 원천 |
| `crawl.dlq` / `parse.dlq` / `embed.dlq` | 1 | delete | 실패 격리 |

`docs.raw`를 영구 보존해 두면 파서를 고친 뒤 오프셋 0부터 다시 흘리기만 하면 되니 재크롤할 일이 없다. `chunks.ready`를 12파티션으로 둔 건 임베더 때문이다. 컨슈머 그룹은 파티션 수를 넘어 늘어나지 않으므로, GPU 노드를 늘릴 수 있는 상한을 여기서 12로 정해 둔 셈이다.

### 본문은 토픽에 싣지 않는다

추출한 본문은 길어야 16만 자, 한글 UTF-8로 약 480KB라 Kafka 기본 메시지 한도 1MB 안에 들어간다. 한도를 넘는 쪽은 원본 HTML이어서, 원본은 gzip으로 블롭 저장소에 두고 `docs.raw`에는 `blob_ref`만 흘린다(클레임 체크 패턴). 토픽과 브로커의 메시지 한도는 10MB로 올려 두었다.

```python
def _path(self, key: str) -> Path:
    if len(key) < 4:
        key = key.rjust(4, "0")
    return self.root / key[:2] / key[2:4] / f"{key}.gz"

def put(self, key: str, data: bytes) -> str:
    path = self._path(key)
    path.parent.mkdir(parents=True, exist_ok=True)
    tmp = path.with_suffix(".gz.tmp")
    tmp.write_bytes(gzip.compress(data, 6))
    tmp.replace(path)  # 원자적 교체. 중간에 죽어도 반쪽 파일이 남지 않는다
    return f"{self.scheme}{key}"
```

키는 `doc_id = sha1(정규화한 제목)`이고 앞 4자로 2단계 샤딩한다. 124만 파일이 65,536개 디렉터리에 흩어지면 디렉터리당 20개 남짓이라, 한 디렉터리에 파일이 몰려 NTFS가 느려질 일은 없다. 단일 노드라면 오브젝트 스토리지보다 파일시스템이 낫다고 판단했다. MinIO는 2026-02에 저장소가 아카이브돼서 아예 후보에 올리지 않았다. 인터페이스(`put`/`get`)는 고정해 뒀으니 다중 노드로 넘어가면 구현체만 SeaweedFS로 바꾸면 된다.

원본을 보관해 둔 덕을 나중에 여러 번 봤다. 청크가 빠진 문서 15개를 복구할 때도, 리다이렉트를 접고 분류 이름을 다시 뽑고 인포박스 관계를 추출할 때도 재크롤 없이 디스크만 다시 읽으면 됐다.

### 멱등성: 다시 받아도 결과가 같게

컨슈머는 `enable.auto.commit=False`로 두고 처리가 끝난 뒤에만 커밋한다. 크래시가 나면 같은 메시지를 다시 받게 되지만 모든 단계가 멱등이라 결과는 그대로다. 멱등을 보장하는 방법은 단계마다 다르다.

| 단계 | 같은 입력을 다시 받으면 |
|---|---|
| 크롤러 | HTML 해시가 `last_hash`와 같으면 하위로 흘리지 않는다 |
| 파서 | `content_hash`가 같고 청크가 실제로 있으면 건너뛴다 |
| 청크 쓰기 | `chunk_id` 기준 upsert. 내용이 바뀐 청크만 `embedded_at`을 비운다 |
| 임베더 | 이미 임베딩됐고 해시가 같은 청크는 인코딩 전에 버린다 |
| Qdrant | 포인트 ID가 `uuid5(chunk_id)`라 같은 청크는 같은 포인트를 덮어쓴다 |

재임베딩 비용은 청크 쓰기 단계의 upsert에서 갈린다.

```sql
INSERT INTO chunks
  (chunk_id, doc_id, seq, section_id, heading_path, text, content_hash)
VALUES (%s,%s,%s,%s,%s,%s,%s)
ON CONFLICT (chunk_id) DO UPDATE SET
  section_id   = EXCLUDED.section_id,
  heading_path = EXCLUDED.heading_path,
  text         = EXCLUDED.text,
  content_hash = EXCLUDED.content_hash,
  embedded_at  = CASE WHEN chunks.content_hash = EXCLUDED.content_hash
                      THEN chunks.embedded_at ELSE NULL END
```

나무위키 문서는 14일마다 재방문한다. 문단 하나 바뀌었다고 그 문서의 청크 수십 개를 전부 다시 임베딩하면 GPU가 버티지 못한다. 그래서 해시가 같은 청크는 `embedded_at`을 그대로 두고, 바뀐 청크만 임베더가 다시 보게 했다. 임베더도 같은 해시 비교를 하기 때문에 크래시 후 이미 끝낸 구간을 다시 받아도 GPU를 쓰지 않는다. 이 검사가 없을 때는 한 번 재시작하는 바람에 청크 4,352개를 괜히 다시 인코딩했다.

### 분산이 실제로 필요한 구간은 하나였다

단계를 나눴다고 해서 모든 단계가 분산으로 이득을 보는 건 아니다.

| 단계 | 병목 | 노드를 늘리면 |
|---|---|---|
| 크롤 | 네트워크 대기, 상대 서버 배려 | 늘리면 안 된다 |
| 파싱 | CPU | 14코어 단일 노드로 충분하다 |
| 임베딩 | GPU | 선형으로 빨라진다 |
| 벡터 검색 | 메모리 | 샤딩이 필요하다 |

크롤러도 컨슈머 그룹으로 만들긴 했지만 목적은 장애 격리였다. 동시 요청 수는 정책 값(4)으로 묶어 두었고, 프로세스를 늘려서 속도를 올리지는 않는다. 배치 DAG(Airflow, Spark) 대신 스트리밍을 택한 것도 크롤이 수십 시간 걸리는 동안 GPU를 놀리고 싶지 않아서였다. 크롤러가 첫 문서를 넣으면 그때부터 임베더가 소비를 시작한다.

## 3. 크롤링 정책

나무위키 robots.txt는 `/w/`를 허용하고 Cloudflare 챌린지도 없다. 그래도 나무위키는 "크롤링은 서버 부담이니 덤프를 받으라"고 안내하고 있다. 허용한다고 해서 환영한다는 뜻은 아니어서, 보호 장치는 설정값에 맡기지 않고 코드로 강제했다.

| 항목 | 값 |
|---|---|
| 동시 요청 | 4 (`NW_CRAWL_CONCURRENCY`) |
| 요청 간 최소 간격 | 도메인 전역 100ms |
| 서킷 브레이커 | 1분 안에 429/5xx 10회면 10분 정지 |
| User-Agent | 비영리 연구 목적과 연락처 자리를 담은 ASCII 식별자 (기본값은 자리표시자) |
| 경로 | robots.txt Allow 경로만 (`/w/`, `/sidebar.json`) |
| 404 | 재시도하지 않고 90일 뒤 재확인, 하위 단계에 삭제 지시 |

### 락 없는 속도 제한

```python
class RateLimiter:
    def __init__(self, min_interval_s: float) -> None:
        self.min_interval = min_interval_s
        self._next_at = 0.0

    async def acquire(self) -> None:
        now = time.monotonic()
        slot = max(now, self._next_at)
        self._next_at = slot + self.min_interval
        delay = slot - now
        if delay > 0:
            await asyncio.sleep(delay)
```

처음엔 `asyncio.Lock`으로 감쌌다가 두 번째 배치부터 죽었다. 크롤러는 배치마다 `asyncio.run()`으로 새 이벤트 루프를 만드는데, Lock은 처음 만들어진 루프에 묶여 있어서 "bound to a different event loop"를 낸다. 사실 지금 구조에서는 락이 없어도 된다. `now`를 읽고 `_next_at`을 갱신하는 사이에 `await`가 없으니 단일 스레드 이벤트 루프에서는 이 구간이 원자적으로 실행된다. 각 태스크는 자기 슬롯을 예약하고 그 시각까지만 잔다.

서킷 브레이커는 1분 창 안에서 실패한 시각을 모아 두다가 문턱을 넘으면 열린다.

```python
def record_failure(self) -> None:
    now = time.monotonic()
    self._failures = [t for t in self._failures if now - t < self.window]
    self._failures.append(now)
    if len(self._failures) >= self.threshold:
        self._open_until = now + self.cooldown
        self._failures.clear()
        log.warning("서킷 열림, %.0f초 정지", self.cooldown)
```

상대 서버가 429나 5xx를 내기 시작했으면 이미 버거운 상태다. 거기에 재시도로 계속 두드리면 상황만 나빠진다.

### 응답이 HTML인지 확인한다

초기에 블롭 저장소에 HTML 대신 압축 바이너리가 쌓인 적이 있다. `Accept-Encoding`에 `br`을 직접 넣었는데 httpx에 brotli 디코더가 깔려 있지 않았다. 그래서 서버가 brotli로 보낸 바이트가 디코딩되지 않고 그대로 저장됐다. 상태 코드가 200이니 오류도 전혀 나지 않는다. 지금은 httpx가 실제로 풀 수 있는 인코딩만 광고하도록 헤더를 비워 두고, 저장하기 전에 가드를 하나 둔다.

```python
body = resp.content
head = body[:1024].lstrip().lower()
if not (head.startswith(b"<!doctype") or head.startswith(b"<html") or b"<html" in head):
    return FetchResult(
        title, 200, None, elapsed,
        f"HTML이 아닌 응답 (content-encoding={resp.headers.get('content-encoding')!r}, "
        f"{len(body)}B)",
    )
```

비슷한 일로 User-Agent에 한글을 넣었다가 요청이 전부 실패한 적도 있다. HTTP 헤더에는 ASCII만 쓸 수 있다.

### 신선도는 3층으로

| 층 | 방식 | 지연 | 역할 |
|---|---|---|---|
| 1 | `sidebar.json` 10초 폴링 | 초 단위 | 편집 즉시 큐잉 (priority 10) |
| 2 | `next_due_at` 14일 재방문 | 최대 14일 | 1층이 놓친 편집 회수 |
| 3 | `content_hash` 비교 | | 바뀌지 않은 문서의 재임베딩 차단 |

비용을 가르는 건 3층이다. 이 층이 없으면 14일마다 코퍼스 전체를 다시 임베딩해야 한다. 그리고 전수 크롤에 70시간쯤 걸리는 사이에도 문서는 계속 바뀌기 때문에 일관된 스냅샷은 원리상 만들 수 없다. 그래서 검색 결과마다 문서의 최근 수정 시각과 수집 시각을 함께 보여 준다.

### BFS는 가치 순서가 아니다

프런티어는 시드에서 링크를 따라 퍼지는 BFS로 채웠다. 그런데 코퍼스를 5천에서 5만 문서로 늘리는 도중에 404 비율이 2%에서 11%로 뛰었고, 404가 난 제목을 보니 전부 윤충 종 이름이었다.

```text
긴다리타원안갑윤충 · 고깔협관윤충 · 두각추돌기협관윤충
필로디나 운둘라타 · 트리코케르카 콜라리스
```

생물 분류 목록 문서 하나에 걸린 빨간 링크(존재하지 않는 문서) 수백 개가 고스란히 큐에 들어와 있었다. 당시 아직 수집하지 않은 프런티어를 인링크 수별로 나눠 보면 다음과 같다.

| 인링크 | 미수집 문서 |
|---|---|
| 50개 이상 | 9,766 |
| 20개 이상 | 25,255 |
| 1개 | 약 22만 |

크롤러가 긁고 있던 건 맨 아래 구간이었다. 여러 문서가 가리키는 제목일수록 실제로 있을 가능성도 검색될 가능성도 높으니 우선순위를 인링크 수로 매겼다. PageRank는 이미 수집한 문서에만 값이 있어서 쓰지 않았다. 아직 받지 않은 문서의 순서를 정하는 데는 인링크 수가 맞다.

```python
# priority 는 낮을수록 먼저다. sidebar 가 알려준 실시간 변경(10)보다는 뒤에 둔다.
TIERS = [(50, 40), (20, 60), (5, 90), (2, 130), (1, 180)]

# 낮은 문턱부터 적용한다.
for lo, pri in sorted(TIERS):
    n = conn.execute(
        """UPDATE crawl_state cs SET priority = %s
             FROM _indeg i
            WHERE i.title = cs.title
              AND i.n >= %s
              AND cs.priority > 10        -- 실시간 변경분은 건드리지 않는다
              AND cs.priority <> %s""",
        (pri, lo, pri),
    ).rowcount
```

이 부분에서 한 번 실수했다. 처음엔 티어를 리스트 순서대로, 그러니까 높은 문턱(50+)부터 적용했다. 인링크가 621개인 제목은 50+ 조건과 1+ 조건에 모두 걸리기 때문에 나중에 실행된 1+ 갱신이 앞의 값을 덮어쓰고, 결국 가장 느슨한 티어가 남는다. `홍콩`이 최하위 등급을 받은 걸 보고서야 알았다. `sorted(TIERS)`로 낮은 문턱부터 적용하면 더 엄격한 조건이 마지막에 덮어쓴다. 고치고 나니 다음 크롤 대상이 이렇게 바뀌었다.

| | 다음 크롤 대상 |
|---|---|
| 전 | 긴다리타원안갑윤충, 트리코케르카 콜라리스 … |
| 후 | 홍콩(621), 2003년(556), 한국-브라질 관계(549), 청나라(457) |

## 4. 파싱과 청킹

### CSS 클래스는 쓰지 않는다

나무위키의 CSS 클래스명은 `_0MSSsdmG` 같은 빌드 해시라 프론트엔드를 배포할 때마다 바뀐다. 클래스 셀렉터에 의존한 추출기는 어느 날 예고 없이 빈 문자열을 뱉게 된다. 그래서 잘 바뀌지 않는 앵커만 골라 썼다.

| 앵커 | 쓰는 곳 | 바뀌기 어려운 이유 |
|---|---|---|
| `<h2><a id='s-4.1'>` | 섹션 경계와 계층 | 외부 링크가 `#s-4`로 참조한다 |
| 라이선스 고지 "이 저작물은 … CC BY-NC-SA 2.0 KR" | 본문 끝 | 법적 고지라 빠질 수 없다 |
| `<h1>` | 문서 제목, 리다이렉트 판별 | |
| `<time datetime=…>` | 최근 수정 시각 | |
| `<details><summary>펼치기 · 접기` | 접이식 네비게이션 틀 제거 | 표준 HTML 요소다 |

섹션 ID의 점 표기가 그대로 헤딩 계층을 나타낸다. `s-4.1`은 깊이 2이고 부모는 `s-4`다.

```python
_SEC_ID = re.compile(r"""\bid=['"](s-[0-9]+(?:\.[0-9]+)*)['"]""")

level = sid.removeprefix("s-").count(".") + 1
```

본문은 첫 섹션 앵커가 달린 헤딩부터 라이선스 고지 직전까지로 잡는다. 섹션 앵커가 없는 짧은 문서는 `</time>` 뒤부터다. `<time>` 정규식 매치는 태그 안쪽에서 끝나기 때문에 거기서 자르면 `data-v-…>` 같은 태그 잔해가 본문 첫 줄에 섞인다. 그래서 `</time>` 뒤에서 자른다.

추출한 텍스트에서 제어문자도 지운다. PostgreSQL의 `text` 타입에는 NUL(0x00)을 넣을 수 없어서, 그대로 두면 NUL 하나 때문에 그 문서의 INSERT 전체가 `DataError`로 실패한다.

## 5. 임베딩

### 모델을 하나로 묶지 않았다

처음엔 BGE-M3 하나로 dense와 sparse를 모두 처리할 생각이었다. 모델 하나가 dense, sparse, colbert 세 헤드를 전부 주기 때문이다. 그런데 공개 한국어 검색 벤치마크(Korean-MTEB-Retrieval-Evaluators, NDCG@10)를 보고 나니 그 계획을 고집할 이유가 별로 없었다.

BGE-M3의 dense는 같은 0.5B 그룹에서 가장 낮았다. KURE-v1은 저장소에 `sparse_linear.pt`가 없는 dense 전용 모델이라, 이쪽 dense 이득을 챙기려면 sparse 모델을 따로 붙여야 했다. 마침 PIXIE-Splade가 0.1B로 작으면서 BM25보다 0.26 높았다. 리랭커는 질의 때 후보 100개에만 돌고 색인 비용이 0이라 넣었다. 참고로 벤치마크 표의 dense 1위는 PIXIE-Spell-Preview-1.7B의 0.7882, 리랭커 1위는 PIXIE-Spell-Reranker-Preview-0.6B의 0.8168이다.

다만 이 벤치마크를 곧이곧대로 믿지는 않았다. 세 부문 모두 telepix 모델이 1위인데, 벤치마크 관리자와 그 회사의 관계를 따로 확인하지 못했기 때문이다. 그래서 모델 ID는 전부 환경변수로 받게 해 두고, 나무위키 질의로 직접 비교하는 하네스(`eval_models.py`)를 만들었다. 이 비교는 아직 끝내지 못했다.

### 0.1B 모델이 시간의 83%를 쓴다

![dense와 sparse 임베딩 비용](/assets/img/posts/namuwiki-rag/embed-cost-light.png){: .light }
![dense와 sparse 임베딩 비용](/assets/img/posts/namuwiki-rag/embed-cost-dark.png){: .dark }
_청크 32개를 GPU에서 분리 측정. 피크 VRAM은 dense 2,654MB, sparse 1,576MB_

파라미터가 5분의 1밖에 안 되는 sparse 모델이 임베딩 시간의 83%를 차지했다. 출력 크기 때문이다. SPLADE는 MLM 헤드의 어휘 로짓 `(배치 × 길이 × 250,002)`를 통째로 만든 뒤 시퀀스 축으로 max 풀링한다. 배치 16, 길이 512이면 이 텐서 하나가 fp16으로 약 4GB이고, 순진하게 짜면 중간 텐서가 세 벌 생긴다. 실제로 배치 16에서 RAM을 8.7GB 잡아먹으면서 머신 전체가 느려졌다.

여기서는 `log1p(relu(·))`가 단조 비감소 함수라는 성질을 썼다. 단조 함수는 max와 적용 순서를 바꿔도 결과가 같다.

$$
\max_{l} \log\bigl(1 + \mathrm{relu}(x_l)\bigr) = \log\bigl(1 + \mathrm{relu}(\max_{l} x_l)\bigr)
$$

그래서 풀링부터 하고 변환은 그 결과인 `(B, V)`에만 건다.

```python
logits = self.model(**enc).logits
# 패딩 위치는 최댓값 후보에서 제외한다
mask = enc["attention_mask"].unsqueeze(-1).bool()
logits = logits.masked_fill(~mask, float("-inf"))
pooled = logits.amax(dim=1)                  # (B, V)
del logits
pooled = torch.log1p(torch.relu(pooled)).float()
for row in pooled:
    nz = torch.nonzero(row, as_tuple=False).squeeze(-1)
    out.append(SparseVec(indices=nz.tolist(), values=row[nz].tolist()))
```

그래도 남는 로짓 한 벌은 sparse 배치를 2로 줄여서 감당한다. dense는 배치 16으로 돌리는데, GPU 경합 중에 재 보니 배치 32가 16보다 4배 느렸다. dense 모델의 `max_seq_length`도 기본값 8192에서 512로 낮췄다. 청커가 850자로 자르니 그보다 길게 잡아 봐야 어텐션 비용만 낭비된다.

전체 임베딩 시간을 처음엔 30~60시간으로 봤는데, 900만 청크 기준으로 환산해 보니 107~142시간이 나왔다. 같은 GPU에서 강화학습 훈련이 2.9GB를 쥐고 돌던 경합 상태에서 잰 처리량이라 처리량으로는 하한, 시간으로는 상한이다. 최종 코퍼스는 210만 청크였다.

### GPU를 공유하면 OOM 대신 조용히 느려진다

Windows에는 Linux의 CUDA MPS가 없다. WDDM은 VRAM이 모자라도 OOM을 내지 않고 호스트 RAM으로 페이징해 버린다. PCIe를 오가느라 100배쯤 느려지는데 에러는 없으니 겉으로는 멈춘 것처럼 보인다. 32청크 배치 하나에 2.6시간이 걸린 적도 있다. 그때 GPU 자체는 멀쩡했고(순수 matmul 10.3 TFLOPS) 여유 VRAM만 부족했다.

애초에 여유 VRAM을 판정하는 방법이 틀려 있었다. `torch.cuda.mem_get_info()`는 다른 프로세스가 4GB를 쥐고 있는데도 "여유 5,075MB"라고 답했고, 그 상태로 1,083MB짜리 모델을 올리자 여유가 0이 됐다. 같은 시점에 `nvidia-smi`는 4,035MB 사용 중이라고 정확히 보여 주고 있었다. 그래서 지금은 `nvidia-smi` 값을 읽는다.

```python
out = subprocess.run(
    ["nvidia-smi", "--query-gpu=memory.used,memory.total",
     "--format=csv,noheader,nounits"],
    capture_output=True, text=True, timeout=15, check=True,
).stdout.strip().splitlines()[0]
used, total = (float(x.strip()) for x in out.split(","))
return total - used
```

필요량도 가중치만 세서는 빗나간다. CUDA 컨텍스트와 캐싱 할당자 예약분, cuBLAS 워크스페이스 몫으로 1,200MB를 더 잡았다. 이 확인은 한 번 하고 끝내면 의미가 없어서 배치마다 여유가 생길 때까지 기다리도록 했다. 상대 작업이 메모리를 0~4GB 사이로 오르내리는 바람에, 확인하고 9분 뒤에 모델 로딩이 18배 느려진 일도 있었다. 여유 배수는 처음에 1.15로 잡았는데, 실제로는 2,793MB면 충분한 상황에서 3,481MB를 요구해서 328MB 차이로 13시간을 기다리기만 했다. 지금은 1.05로 둔다.

그래도 멈추는 경우에 대비해 배치마다 감시견을 붙였다. CUDA 호출은 파이썬에서 인터럽트할 수 없으니 스레드가 600초를 기다렸다가 `os._exit(75)`로 프로세스를 내린다. 커밋하기 전이니 메시지는 다시 전달된다.

Kafka 쪽에서도 비슷한 정지를 겪었다. 임베더가 128청크씩 모아 처리하던 시절, GPU 경합 때문에 한 배치가 `max.poll.interval.ms`(15분)를 넘기자 브로커가 컨슈머를 그룹에서 내보냈다. 이때 프로세스는 살아 있는데 진행만 멈춘다. 배치를 32로 줄이고 나서는 정상 속도에서 한 사이클이 10초 안팎이라 한도까지 여유가 넉넉하다.

## 6. 하이브리드 검색과 리랭커

```text
질의
 ├─ dense  top-100 (KURE-v1) ─┐
 └─ sparse top-100 (SPLADE)  ─┴─ RRF 융합 ─ 리랭커 (bge-reranker-v2-m3) ─ PageRank 동점 보정 ─ top-k
```

dense 코사인 유사도와 SPLADE 내적은 점수 스케일이 달라서 가중합으로 섞으면 불안정하다. 그래서 순위만 보는 RRF로 합쳤다.

$$
\mathrm{RRF}(d) = \sum_{r \in \{\text{dense},\,\text{sparse}\}} \frac{1}{k + \mathrm{rank}_r(d)}
$$

융합은 Qdrant 서버 쪽에서 처리하고, `k`는 Qdrant 기본값을 그대로 썼다.

```python
return _qdrant().query_points(
    collection_name=SETTINGS.collection,
    prefetch=[
        models.Prefetch(query=dvec, using="dense", limit=candidates, filter=flt),
        models.Prefetch(
            query=models.SparseVector(indices=svec.indices, values=svec.values),
            using="lexical", limit=candidates, filter=flt,
        ),
    ],
    query=models.FusionQuery(fusion=models.Fusion.RRF),
    limit=candidates,
    with_payload=True,
).points
```

dense 벡터는 원본을 디스크에 두고 RAM에는 int8 스칼라 양자화본만 올린다. 설계 단계에서 900만 청크 기준으로 계산해 보니 float32 원본은 36.9GB, int8은 9.2GB였고, 32GB 노트북에서 버틸 수 있는 쪽을 택했다. 컬렉션은 처음부터 4샤드로 만들었다. OSS Qdrant에서는 샤드 수를 나중에 늘리려면 재색인을 해야 해서 미리 정해 뒀다.

### PageRank는 동점에만

융합된 후보 100개는 리랭커가 다시 점수를 매긴다. PageRank는 리랭커 점수가 소수 둘째 자리까지 같을 때 순서를 가르는 데만 쓴다.

```python
def sort_key(item):
    idx, score = item
    pr = (meta.get(res[idx].payload["doc_id"], {}) or {}).get("pagerank") or 0.0
    return (round(score, 2), pr)

ranked = sorted(ranked, key=sort_key, reverse=True)[:top_k]
```

관련도 점수에 PageRank를 더해 버리면 인기 문서가 정확한 답을 밀어내기 쉽다. 이보다 강하게 섞을지는 자체 평가 데이터가 쌓이고 나서 정하기로 했다. 동점 후보가 잘리지 않도록 리랭커 단계에서는 `top_k * 3`개를 받아 둔다.

### KG-1: 엣지 테이블 대신 배열

설계할 때는 전수 수집 시 엣지를 10억 개로 잡았다. 최종 밀도(문서당 321)로 124만 문서를 환산하면 약 4억 개다. 10억 기준이면 별도 엣지 테이블이 sha1 40자 × 2 × 10억 = 80GB라 과하다고 판단했다. `documents.outlinks TEXT[]`에 배열로 넣으면 TOAST 압축이 적용되고, 역링크도 GIN 인덱스로 질의할 수 있다.

```sql
SELECT title FROM documents WHERE outlinks @> ARRAY['김연아'];
```

PageRank 계산에서 엣지를 파이썬 객체로 들고 있으면 메모리가 버티지 못해서 처음부터 numpy CSR(int32)로 만든다. `outlinks`는 서버 사이드 커서로 스트리밍한다. 나가는 링크가 없는 문서의 점수는 반복마다 전체에 고르게 나눠 줘서 총합이 새지 않게 했고, 누적은 `np.add.at` 대신 `np.bincount`로 한다.

```python
leaked = damping * pr[dangling].sum() / n
src_scores = np.where(dangling, 0.0, pr / np.maximum(outdeg, 1.0))
src_of_edge = np.repeat(np.arange(n, dtype=np.int64), np.diff(indptr))
contrib = np.bincount(indices, weights=src_scores[src_of_edge], minlength=n)
new = base + leaked + damping * contrib
```

오히려 결과를 쓰는 데서 시간이 많이 들었다. 112,255건을 한 행씩 UPDATE하니 33분이 걸렸고, 그동안 서버는 `ClientRead` 상태로 파이썬만 기다렸다. 그래서 `COPY`로 임시 테이블에 한꺼번에 넣고 조인 UPDATE 한 번으로 끝내게 바꿨다. 다만 `documents`에 `outlinks`와 `categories` GIN 인덱스가 걸려 있어서, 어떤 컬럼을 갱신하든 튜플이 다시 쓰이고 배열 원소가 인덱스에 다시 들어간다. 한 번에 약 3,600만 항목이다. 왕복 비용은 없앴어도 이 비용은 그대로 남았다.

PageRank 상위 10위 안에 `편집 요청`과 `크리에이티브 커먼즈 라이선스`가 올라온 적도 있다. 둘 다 실제로 있는 문서이긴 한데, 그 링크는 모든 페이지에 붙는 UI에서 온다. 처음엔 인링크 비율로 거르려 했지만 라이선스 문서가 16.3%로 `서울특별시`(16.5%)와 `영국`(15.2%) 사이에 끼어 있었다. 문턱을 어디에 잡든 진짜 허브까지 같이 빠진다. 결국 두 제목을 그래프에서 명시적으로 빼고 점수도 비웠다.

링크를 본문에서만 수확하는 방법도 있었지만 그러면 인포박스까지 사라진다. 인포박스가 첫 섹션 앵커보다 위에 있기 때문이다. 대한민국 문서로 보면 링크가 1,468개에서 839개로 줄었고, 빠진 것 가운데 `.kr`, `1987년`, `24절기` 같은 인포박스 링크가 있었다. KG-2에서 가장 쓸모 있는 소스를 UI 링크 두 개 때문에 버릴 수는 없었다. 그래서 본문 텍스트용 `body_html`과 링크 수확용 `link_html`을 나누고, 후자는 문서 상단부터 라이선스 고지 직전까지로 잡았다.

### KG-2: 관계는 규칙으로 뽑는다

`outlinks`가 알려 주는 건 "A가 B를 가리킨다"까지다. 김연아의 국적이 대한민국이라는 사실과 김연아 문서가 대한민국을 언급했다는 사실은 서로 다르다. 산문에서 LLM으로 트리플을 뽑자니 비싸고 정밀도도 낮다. 앞서 했던 ontology 프로젝트에서도 산문 코퍼스로 시작했다가 관계 46개에서 막혔고, 로컬 LLM 관계 추출의 recall은 25%였다. 그래서 여기서는 나무위키에서 결정론적으로 뽑히는 네 갈래만 썼다.

| 출처 | 관계 | 예 | 건수 |
|---|---|---|---|
| 인포박스 표 | 라벨이 술어 | `손흥민 --국적--> 대한민국` | 302,332 |
| 분류 | `INSTANCE_OF` | `김연아 --INSTANCE_OF--> 1990년 출생` | 669,562 |
| 슬래시 제목 | `PART_OF` | `김일성/생애 --PART_OF--> 김일성` | 4,429 |
| 리다이렉트 | `SAME_AS` | `옐로우나이프 --SAME_AS--> 옐로나이프` | |

인포박스에서는 라벨이 든 `<strong>` 셀과 바로 뒤의 값 셀을 정규식으로 짝짓는다. 여기서 쓰는 `wiki-link-internal` 같은 클래스는 나무위키가 의미를 담아 직접 붙인 이름이어서, 빌드 해시와 달리 배포 때마다 바뀌지 않는다. 노이즈는 두 단계로 걸렀다.

### 타입 계층: 일곱 개로 닫았다

관계가 두 문서 사이의 일이라면 타입은 문서 자체가 무엇인지를 나타낸다. 타입은 인물, 장소, 조직, 작품, 사건, 생물, 개념 일곱 개로 닫았다. 클래스가 많아지면 경계가 흐려지고 어디에 넣어야 할지 애매한 문서가 늘어난다. 판정할 때는 인포박스 술어를 먼저 보고(`출생`과 `학력`이 있으면 사람), 술어가 없으면 분류 이름을 본다. 규칙은 오분류를 하나씩 마주칠 때마다 늘었다.

| 오분류 | 원인 | 규칙 |
|---|---|---|
| 토트넘 홋스퍼 FC = 작품 | `감독`은 영화 감독이자 축구 감독 | `감독`, `작곡가`, `장르`를 작품 신호에서 제외 |
| 당나라 = 인물 | 왕조 문서에 황제의 `사망`이 있다 | 술어는 장소를 인물보다 먼저 본다 (`수도`, `통화`는 사람에게 안 붙는다) |
| 2020년 = 작품 | 분류 `2020년 영화` | 자기 제목이 들어간 분류는 건너뛴다 |
| 카타르 = 작품 | 분류 `아시안 게임 개최국` | 분류의 마지막 단어(머리명사)만 본다 |
| 문화방송 = 작품 | 뒤쪽 분류가 자사 드라마·예능 | 분류는 앞에서 6개만 센다 |

타입이 붙고 나서는 관계가 앞뒤가 맞는지도 검사할 수 있게 됐다. `임진왜란 이순신 해전`을 검색하면 `부산포 해전 --가족--> 방수진`이 사실로 나왔다. 해전 문서 안에 지휘관의 인포박스가 들어 있어서 추출기가 지휘관의 가족을 해전의 사실로 읽었다. 이제는 사람에게만 성립하는 술어가 사람이 아닌 문서에 달려 있으면 보여 주지 않는다.

```sql
SELECT r.subject, r.predicate, r.object
  FROM relations r
  LEFT JOIN documents d ON d.title = r.subject
 WHERE r.subject = ANY(%s) AND r.source = 'infobox'
   AND NOT (r.predicate = ANY(%s)           -- 출생, 사망, 학력, 배우자, 가족, 직업 …
            AND coalesce(d.entity_type, '') <> '인물')
 ORDER BY d.pagerank DESC NULLS LAST, r.predicate
 LIMIT %s
```

행 자체는 테이블에 그대로 두고, 틀린 사실이 답으로 나가기 직전에만 거른다. 이제 같은 질의를 하면 `소속 --> 삼도수군통제사`가 나온다.

### KG-3: 커뮤니티로 이웃 고르기

커뮤니티는 링크 밀도로 찾은 주제 덩어리다. 사람이 단 분류와 달리 실제 링크 구조에서 나오니 분류가 없거나 엉성한 문서도 함께 묶인다. 링크 방향은 버리고 무향 그래프에서 Leiden을 돌렸다. Louvain은 서로 연결되지 않은 조각을 한 커뮤니티로 묶어 버릴 수 있는데, Leiden은 이 결함을 고친 알고리즘이다. 56,703노드, 무향 엣지 740만 개 시점에 C 구현(igraph)으로 몇 분 걸렸고 모듈성은 0.6702가 나왔다. 최종 코퍼스에서는 커뮤니티 29개, 모듈성 0.69였다. 크기 5 미만 커뮤니티는 비워 두기 때문에 112,255건 중 112,251건이 배정됐다.

그래프 화면에서 이웃을 고를 때 이 커뮤니티를 쓴다. PageRank만으로 고르면 `손흥민` 주위가 연도와 국가로 채워지는데, 링크는 많아도 주제와는 거리가 멀다. 같은 커뮤니티를 먼저 고르게 하자 축구 선수, 프리미어 리그, 박지성으로 바뀌었다. 날짜·연도·요일 문서는 기본으로 감춘다. 드라마 `넝쿨째 굴러온 당신`을 그려 보면 화면 절반이 `4월 1일`, `2012년`, `토요일`이었고, 이걸 감추자 `한국방송공사`, `KBS 2TV`, `시청률`이 드러났다.

두 문서 사이의 최단 경로(`/api/graph/path`)는 양쪽에서 동시에 넓혀 가는 양방향 BFS로 찾는다. 홉마다 분기가 수백 배씩 늘어서 단방향으로는 3홉이면 수백만 노드에 이르지만, 양쪽에서 절반 깊이씩만 들어가면 탐색량이 제곱근 수준으로 줄어든다. 여기서도 달력 문서는 빼야 했다. 그냥 두면 `손흥민 → 1월 6일 → 이순신`처럼 아무 두 문서나 날짜 하나를 거쳐 2홉으로 이어진다. 빼고 나니 `손흥민 → 김연아 → 이순신`이 나왔다.

커뮤니티별 LLM 요약은 아직 만들지 않았다. 하루에 문서 33,600개가 바뀌는 코퍼스라 요약을 매번 새로 만들 수는 없고, 바뀐 커뮤니티만 무효화하는 증분 갱신부터 설계해야 한다.

## 8. 오류 없이 데이터만 틀어지는 결함

이 프로젝트에서 잡기 까다로웠던 버그는 하나같이 예외를 던지지 않았다. 프로그램은 멀쩡히 도는데 데이터만 조용히 틀어지거나 빠져 있었다.

| 증상 | 원인 | 어떻게 알았나 |

| 가장 큰 문서 15개가 검색에서 빠짐 | 문서 행과 청크를 따로 커밋, 재파싱은 해시가 같아 건너뜀 | 스모크 테스트 |
| 문서 5.2%가 별칭 제목으로 저장 | 크롤러가 리다이렉트를 따라감 | 카나리아 |
| 서비스를 띄울 때마다 메시지 유실 | 파티션 할당 대기 중 받은 레코드를 버림 | 컨슈머 랙 1이 안 줄어듦 |
| 임베딩 안 된 청크 140개 | 실패 배치를 DLQ로 보내고 오프셋 커밋 | `embedded_at IS NULL` 집계 |
| 문서 9,869건의 분류 이름이 틀림 | 링크 텍스트에서 분류 이름을 읽음 | 경기도가 인물로 분류됨 |
| 컨슈머 그룹이 0건만 반환 | kafka-python이 Python 3.14 selectors와 비호환 | 그룹 없는 소비는 됨 |
| 카나리아가 영영 재검증 안 됨 | 안 바뀐 문서는 단축 경로를 탐 | 마지막 검사 시각이 멈춤 |

### 청크 없는 문서 15개

미국, 일본, 한국사, 삼성전자처럼 가장 큰 문서들이 검색에서 통째로 빠져 있었다. 처음 만든 파서는 autocommit 연결에서 문서 행과 청크를 따로 썼기 때문에, 청크 INSERT만 실패하면 문서 행은 커밋된 채로 남았다. 4장에서 말한 NUL 문자도 15건의 원인 후보 가운데 하나였다. 그 뒤 같은 문서가 다시 들어오면 `content_hash`가 같으니 "변경 없음"으로 건너뛰고, 그 문서는 영영 복구되지 않는다. 15개가 정확히 어떤 실패 경로를 탔는지는 끝내 하나로 특정하지 못했다.

```python
# 해시가 같아도 **청크가 실제로 있는지** 확인한다.
row = conn.execute(
    """SELECT d.content_hash,
              EXISTS (SELECT 1 FROM chunks c WHERE c.doc_id = d.doc_id) AS has_chunks
         FROM documents d WHERE d.doc_id = %s""",
    (did,),
).fetchone()
if (
    row
    and row["content_hash"] == msg["content_hash"]
    and row["has_chunks"]
    and not is_canary
):
    return "unchanged"

# ... 추출, 리다이렉트 접기, 청킹, 링크 수확 생략

# 문서 행과 청크는 **한 트랜잭션**으로 쓴다.
with conn.transaction():
    _write(conn, producer, msg, did, title, ex, chunks, body_len, outlinks)
```

고친 곳은 네 군데다. 문서 행과 청크를 한 트랜잭션으로 묶었고, "변경 없음" 판정에 `has_chunks`를 넣었다. 스모크 테스트에는 "본문은 있는데 청크가 없는 문서" 검사를 추가했고, `repair_chunkless.py`로 블롭에서 15개를 다시 추출했다. 원인은 특정하지 못했어도 원본 HTML이 남아 있었으니 복구 자체는 결정적으로 할 수 있었다.

### 리다이렉트를 따라가면 생기는 중복

추출 수율 카나리아는 기준 문서 5개의 추출 길이를 지켜보다가 ±30%를 벗어나면 경보를 울린다. CSS 셀렉터를 쓰지 않아도 추출기는 언젠가 깨지기 마련이고, 깨진 추출기는 빈 문자열로 수백만 청크를 오염시키면서도 아무 신호를 내지 않는다. 이 카나리아가 `파이썬`에서 -41.8%로 경보를 냈는데 나머지 4개는 ±0.0%였으니, 추출기 문제는 아니었다.

`파이썬`은 `Python`으로 넘어가는 리다이렉트다. 크롤러가 `follow_redirects=True`로 따라가면서 정식 문서의 내용이 별칭 제목 아래 저장돼 있었다. 표본 300개 중 5.3%, 전수로 보면 255개(5.2%)가 이런 상태였다.

| 저장된 제목 | 실제 `<h1>` |
|---|---|
| 픽사 | 픽사 애니메이션 스튜디오 |
| 3.1절 | 삼일절 |
| 2016 리우 올림픽 | 2016 리우데자네이루 올림픽 |

두 제목이 모두 수집되면 같은 내용을 두 번 임베딩하게 되고(이미 69건이 중복이었다) 그래프 노드가 둘로 갈라져 PageRank가 나뉘며, 검색 결과에도 같은 문단이 두 번 뜬다. 나무위키는 리다이렉트를 따라간 뒤에도 `<h1>`에 정식 제목을 보여 준다. 그래서 파서는 `<h1>`이 요청한 제목과 다르면 정식 제목을 문서 정체성으로 삼고, 별칭은 `redirects` 테이블에 남긴다. 이미 저장된 문서는 `fold_redirects.py`로 블롭에서 다시 접었고, PageRank와 커뮤니티 계산에서는 별칭 링크를 정식 노드로 해석한다. `파이썬`이 `Python`으로 접힌 뒤에는 카나리아도 정식 제목을 따라가게 바꿨다. 그러지 않으면 문서가 없는 제목을 계속 재면서 영구히 오경보를 낸다.

카나리아 자체에도 버그가 두 번 있었다. 한 번은 기준선이 0인 채로 비교하는 바람에 매번 오경보가 났고(첫 성공 파싱을 기준선으로 삼게 고쳤다), 또 한 번은 문서가 바뀌지 않으면 "변경 없음" 단축 경로를 타는 탓에 검사가 아예 돌지 않았다(카나리아 문서는 단축 경로에서 뺐다).

### 기다리는 동안 받은 레코드

청크 하나가 끝까지 임베딩되지 않은 적이 있다. `chunks.ready`에 세 번이나 다시 발행했는데 매번 "0청크"로 끝났고 로그에도 에러가 없었다. 컨슈머 그룹 랙만 1로 남아 있었다.

원인은 공용 폴 루프에 있었다. 구독 직후의 첫 폴은 그룹 조인 때문에 거의 비어 있어서, 할당을 받을 때까지 폴을 돌리며 기다리게 해 놓았는데 그 결과를 버리고 있었다. 그런데 이 폴은 실제로 레코드를 가져온다. 버려진 레코드는 바로 다음 배치가 커밋하면서 오프셋이 지나가 버리니 재전달될 일도 없다. 서비스를 띄울 때마다 메시지를 하나씩 잃을 수 있는 구조였다.

```python
def _await_assignment(self) -> bool:
    deadline = time.monotonic() + self.assign_timeout_s
    while time.monotonic() < deadline:
        if self.consumer.assignment():
            return True
        # 이 폴은 그냥 기다리는 게 아니라 실제로 레코드를 가져온다.
        # 버리면 그 메시지는 영영 사라진다. 받아둔 건 첫 배치로 넘긴다.
        batch = self.consumer.poll(timeout_ms=500)
        if batch:
            self._buffered.extend(
                rec for recs in batch.values() for rec in recs
            )
```

같은 루프에서 `--once` 모드의 종료 조건은 경과 시간으로 판단한다. 준비가 안 된 컨슈머는 폴이 곧바로 돌아오기 때문에, 횟수로 세면 금방 소진되고 큐에 메시지가 남아 있는데도 0건 처리로 끝나 버린다.

### DLQ로 간 청크는 아무도 다시 보내지 않는다

임베딩 배치가 실패하면 메시지를 `embed.dlq`로 보내고 오프셋을 커밋한다. 덕분에 파이프라인은 멈추지 않지만 그 청크들은 DB에 `embedded_at IS NULL`로 남은 채 검색에서 빠진다. Qdrant upsert 타임아웃으로 컨슈머가 쫓겨난 밤을 넘기고 보니 140개가 이렇게 남아 있었다. 청크 텍스트는 이미 DB에 있으므로 `repair_unembedded.py`가 DB에서 곧장 다시 발행한다. 포인트 ID가 `uuid5(chunk_id)`라 몇 번을 돌려도 안전하다.

이 복구 로직은 나중에 재부팅 대비 런처에도 넣었다. 하루에 정전(Kernel-Power 41)과 정상 종료로 두 번이나 꺼진 뒤의 일이다. 컨테이너에 `restart: unless-stopped`를 주고 시작 프로그램 폴더에 런처를 넣어서, 로그온하면 임베딩이 이어지게 했다. 런처는 큐가 비었는데 DB에 미임베딩 청크가 남아 있으면 DB에서 다시 발행하고, 여섯 번을 돌아도 안 되면 사람에게 넘긴다. 남은 청크가 없으면 스스로를 지운다.

### 화면에 보이는 이름과 진짜 이름

나무위키는 분류 링크를 그릴 때 문서 제목과 겹치는 접두어를 생략한다. 예를 들어 `경기도` 문서에서는 `분류:경기도 출신 인물`이 그냥 `출신 인물`로 렌더링된다. 추출기가 분류 이름을 링크 텍스트에서 읽는 바람에 모든 지역 문서가 인물 분류를 단 것처럼 저장됐고, 타입 분류기는 그걸 그대로 믿고 경기도를 인물로 판정했다. 당시 86,157문서 중 9,869건이 틀린 분류를 하나 이상 달고 있었다. `href`에는 접두어까지 들어간 정식 이름이 남아 있어서 그쪽을 읽도록 바꿨다. 분류는 메타데이터라 전량 재파싱할 필요 없이 블롭을 한 번 훑어 갱신했다.

## 9. 한계와 다음 단계

- 답변 생성은 아직 붙이지 않았다. 지금 시스템은 근거 문단과 그래프 사실을 찾아 주는 데서 멈춘다. 설계에는 로컬 LLM으로 답을 쓰고 원문 링크와 CC BY-NC-SA 2.0 KR 고지를 붙이는 단계까지 있지만 모델도 아직 고르지 못했다.
- 모델 품질은 직접 재 보지 못했다. dense·sparse·리랭커는 공개 벤치마크를 보고 골랐는데, 그 벤치마크의 이해충돌 의심은 아직 풀리지 않았다. 처리량만 보면 PIXIE-Rune-Preview가 KURE-v1보다 32% 빨랐지만, 품질 A/B는 `eval_models.py`로 직접 돌려 봐야 한다. 임베딩 처리량 역시 GPU 경합 중에 잰 하한이라 유휴 상태에서 다시 재야 한다.
- 수집은 전수가 아니다. 112,255건은 실질 문서 124만의 9%쯤이고, 프런티어에 985,062건이 대기 중이다. 동시 4개 기준 실측 속도가 초당 4.9문서라 전수 수집에는 약 70시간이 걸린다. BFS가 몇 홉에서 수렴하는지도 아직 모른다.
- 네비게이션 박스가 아직 샌다. `<details><summary>` 형태가 아닌 네비박스는 본문에 섞여 들어오고, 그 바람에 무관한 목록이 검색 결과에 끼어든다.
- 크롬 링크는 이름을 하나하나 지정해서 막았다. `편집 요청`과 라이선스 문서를 명시적으로 뺐을 뿐이라, 다른 UI 링크가 생기면 또 손으로 추가해야 한다. 코퍼스가 커지면 "주제상 무관한 문서들이 일제히 가리키는 대상"을 통계로 거르는 쪽이 맞다.
- `chunks.ready`는 지금 상태로는 재생이 안 된다. 코드를 분석해서 내린 결론이고, 실제로 재생해 보지는 않았다. 파서가 청크 메시지의 키를 `doc_id`로 보내는데 compact 토픽은 키마다 마지막 값만 남긴다. 그래서 로그 클리너가 지나간 구간을 처음부터 재생하면 문서당 마지막 청크(또는 마지막 삭제 지시)만 남는다. "임베딩 모델을 바꾸면 `chunks.ready`만 다시 흘린다"는 설계를 지키려면 키를 `chunk_id`로 바꿔야 한다. 미임베딩 청크 복구는 청크 본문이 DB에 있으니 DB에서 읽어 다시 발행한다.
- KG-3 요약과 그래프 저장소는 아직 정하지 못했다. 커뮤니티별 요약은 증분 무효화 설계가 먼저다. Neo4j로 도메인 층을 내릴 계획도 있는데, 전체 링크망(설계 때 10억으로 잡았고 최종 밀도로 환산하면 약 4억)은 Neo4j Community로 감당하기 어렵다. 그래서 PageRank 상위 문서와 인포박스 관계만 내리려는데, 그 분할 경계를 아직 못 정했다.

돌아보면 아키텍처는 설계 단계에서 잰 숫자들(문서 크기, sidebar 창, 덤프 구조)이 정했고, 운영하면서 생긴 문제는 대부분 소리 없이 지나가는 쪽이었다. 리다이렉트 중복은 카나리아가, 청크 없는 문서는 스모크 테스트가 찾아냈다. 둘 다 그냥 두었으면 오류 하나 없이 지나갔을 결함이다. 다시 만든다면 불변식 점검부터 짜고 나서 파이프라인을 올릴 것 같다.
